# 実装へ何を渡すか — 文書の仕分け

**作成日**: 2026-08-31
**目的**: **このリポジトリは仕様決定のためのリポジトリ**であり、実装は別の場所で行う。
実装場所には**実装に必要な情報だけ**を持っていく。その仕分けを1箇所に決める。

---

## 0. 結論を先に

**いま実装へ渡せる文書は、`SCHEMA.md` と `golden/` だけしかない。**

「何を作るか」（`SIMPLE_VERSION.md`）と「なぜそう決めたか」（`DECISIONS.md`）は揃っているが、
**「どう作るか」を実装者が単独で読める形にした文書が無い。** それが仕様書である。

> **実装の前に仕様書を書く。** 順序は
> **構想（済）→ 仕様書（未）→ 実装**。
> 本文書は仕分けと、仕様書に何を書くかを決める。

---

## 1. 仕分けの原則

| 原則 | 内容 |
|---|---|
| **仕様書は自己完結させる** | **`DECISIONS.md` を参照しないと読めない仕様書は、実装場所に持っていけない。** 根拠が要る箇所は、結論を仕様書に書いたうえで出典を注記する |
| **経緯は持っていかない** | 「なぜ A ではなく B にしたか」は実装には不要。ただし**決定を蒸し返さないため**に本リポジトリに残す |
| **正本を二重に持たない** | `SCHEMA.md` は**移す**（コピーしない）。写しを作れば F-8（追随漏れ）が再発する |
| **測定スクリプトは残す** | 数字の出典。実装には不要だが、仕様を疑ったときに再現できる必要がある |

## 3. 仕様書の構成（提案）

**渡す先は `spec/` 一式。これだけで実装に着手できることを条件にする。**

> **下表のファイル名は提案であり、まだ存在しない**（太字で示す）。`verify_docs.py` が
> 「実在しないファイル参照」として拾わないよう、バックティックを付けていない。

| ファイル | 中身 | 現状 |
|---|---|---|
| **spec/SPEC.md** | **全体像・要件・CLI・設定ファイル・処理フロー・異常時の振る舞い** | **未作成** |
| **spec/SCHEMA.md** | 列定義（現 `docs/SCHEMA.md` を移設） | **完成** |
| **spec/EXTRACTION.md** | **L0 の仕様**。言語別の抽出規則、`resolved_by` の判定順序、ERROR ノードの扱い、閉世界仮定の適用 | **未作成。実装の本体** |
| **spec/REPORTS.md** | **L3a のプラグイン仕様**（受け口・`Artifact`・`requires`）と**5レポートの定義** | **未作成** |
| **spec/TESTING.md** | ゴールデンデータの使い方、受け入れ基準、検証スクリプト | **未作成** |
| **spec/golden/** | 正解データ | **完成** |

### とくに EXTRACTION.md が要る理由

**「どう解くか」がいまどこにも一箇所にまとまっていない。**
判定規則は `DECISIONS.md` の E-1 / E-3 / F-16 に分散し、実際の順序は測定スクリプトの中にしかない。

**実装者が読むべきものは「決定の並び」ではなく「判定の手順」である。** 具体的には:

1. 呼び出し式の形の分類（識別子 / メンバ / 間接）
2. **判定の適用順序**（マクロ → ローカル束縛 → 同一 container → 宣言型 → 型名 static → 閉世界で一意 → 辞書 → 外部）
3. 各段での `status` / `reason` / `resolved_by` / `confidence` の埋め方
4. **オーバーロードの検出と降格**（F-16 決定2）
5. **`base.` は基底から探す**（F-16 決定3）
6. 言語ごとに変わるのは**集合の中身だけ**（F-12 決定2。C# は `{this, base}`、Python は `{self, cls}`、JS は `{this, super}`）

> **F-12 の教訓がここに効く。** 3つのスクリプトが同じ判定を別々に書き直した結果、
> 同じ指標が 53 / 55 / 56 と食い違った。**判定規則を1箇所に書き下ろすのが仕様書の役目**である。

## 4. 実装リポジトリ側で決めること（本リポジトリの範囲外）

仕様書に含めない。実装リポジトリの `CLAUDE.md` 相当で決める。

- パッケージ名・ディレクトリ構成の細部
- 依存管理（`pyproject.toml`）、lint / format の設定
- CI の構成

**ただし B-3（`core/` にロジック、CLI は薄いラッパー、ジョブ設定ファイル、構造化進捗出力）と
§7.3 ルール4（L1 を境界にプラグイン化）は仕様書に書く。** これらは構成の自由ではなく要件だから。
