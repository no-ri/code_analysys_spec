## 1. なぜ凍結したか

フル版の設計を詰めていった結果、`CODE_ANALYSIS_CONCEPT.md` §9.3 で必要なインストールを洗い出したところ、フル構成で以下が必要と判明した。

**重要**: 凍結は「内容に誤りがあるから」ではない。**前提そのものを問い直すため**。フル版の設計は「厳密版」として有効であり、捨てない。

## 2. 重さの根本原因（これが議論の核心）

フル版が重い原因は一点に集約される。**§4.1 の選定基準1「意味解析（名前解決）を持っているか」**である。

```
正確な名前解決が欲しい
  → コンパイラのフロントエンドが要る (libclang / Roslyn / TypeScript Compiler API)
    → それぞれのランタイムが要る (.NET / Node)
      → ビルドコンテキストが要る (compile_commands.json / .sln / tsconfig.json)
        → 利用者が「ビルドが通る状態」を用意しないといけない  ← 最大の負担
```

### 想定用途との突き合わせ

想定用途は「**初見のソースコードの一次解析の補助**」。嬉しいのは全体像の把握。

| 知りたいこと | 名前解決が要るか |
|---|---|
| どのフォルダに何の機能があるか | 不要 |
| どの辺りが詳細解析を要しそうか | 不要 |
| 規模感・構造の偏り | 不要 |
| モジュール間の大まかな依存 | ほぼ不要（import / include 文を読むだけ） |
| 「この関数の呼び元を漏れなく全部」 | **必要**（ここだけフル版の領分） |

> **未検証の見立て（要議論）**: 一次解析という用途は、フル版の能力のごく一部しか使っていない。したがって名前解決を捨てても用途の大半は満たせるのではないか。
> **この見立て自体がまだ検証されていない。** 次セッションではまずここに同意できるかを確認すること。

## 3. 決まっていること（変更しない前提）

詳細と根拠は `OPEN_DECISIONS.md` の「決定事項」にある。**簡易版でもそのまま使える**ものが多い。

| ID | 決定内容 | 簡易版への影響 |
|---|---|---|
| A-1 | `resolution` を `status`（4値）と `reason`（4値）の2列に分離 | **そのまま使える**。簡易版の解けない呼び出しは `status = unresolved` |
| A-2 | `confidence` を `high` / `medium` / `low` の enum で追加 | **そのまま使える**。簡易版の結果は `low` |
| A-3 | `lang` / `extractor` / `snapshot` を全テーブルに持たせる | そのまま使える |
| B-1 | シンボルIDは SCIP 形式。自リポジトリは `local` スキーム | 簡易版では過剰かもしれない（要検討） |
| B-2 | L1 ストアは SQLite（`facts/db.sqlite`） | そのまま使える。追加インストール不要 |
| B-3 | 抽出器は独立プロセス。GUI 後付けのための3つの約束 | 簡易版では単純化できる可能性 |
| B-4 | `snapshot` は `git describe --always --dirty` 相当 | そのまま使える |

**特に重要**: A-1 / A-2 と §7.3 の層分離により、**簡易版の抽出結果とフル版の結果を同じテーブルに混在させられる**設計になっている。簡易版は「フル版の下位互換」として位置づけられる。これを活かすかどうかが E-4。

## 4. 次に議論すること（E 群）

`OPEN_DECISIONS.md` の E 群に4項目ある。**E-2 が起点**。

### E-2（起点）: 「インストール不要」の水準をどこに置くか

| 水準 | 利用者への要求 | 実現手段の見当 |
|---|---|---|
| 完全ゼロ | 単一実行ファイルを置くだけ | Go / Rust で書く。tree-sitter 同梱 |
| ほぼゼロ | ランタイム1つだけ（例: Python のみ） | 標準ライブラリ中心 |
| 軽い | パッケージマネージャで1コマンド | tree-sitter の言語バインディングが使える |

**あわせて決めること**: フル版が要求していた「ビルドコンテキストを利用者に用意させる」という制約を、**課さない**と決めるか。

### E-1: 想定用途の再定義

一次解析の補助として、最小の出力は何か。フル版 §1.1 の目的（正確なコール関係・データの所在）との関係は、置き換えか、部分集合か、別物か。

### E-3: 名前解決を捨てた場合の線引き

**できること（見込み・未検証）**
- ディレクトリ構造マップ（行数・ファイル数・言語構成の分布）
- ファイル / フォルダごとの規模と偏り → 「どの辺りが重いか」
- import / include / using 文の抽出 → モジュール間の大まかな依存図
- 関数・クラスの一覧と位置（構文レベル）
- 命名の語彙集計（フォルダ名・ファイル名）→ 機能推測の材料
- コメント密度、TODO / FIXME の分布 → 「未整理そうな領域」の当たり

**できないこと**
- 正確なコールグラフ（オーバーロード・仮想呼び出し・関数ポインタは解けない）
- 「この変数がどこで書かれるか」の網羅
- 未使用コードの断定
- 型情報

**再評価すべき候補**: フル版 §4.7 は tree-sitter を「まだ抽出器を書いていない言語の暫定対応」と格下げしているが、**簡易版では主力候補**になりうる。ビルドコンテキスト不要で多言語を1つの仕組みでカバーできるため。

### E-4: 簡易版とフル版の関係

独立した別ツールにするか、フル版の下位互換（同じスキーマに `confidence = low` で入れる）にするか。

## 7. 環境メモ（実測済み・再確認不要）

次セッションで同じ調査を繰り返さないための記録。

- `sqlite3` は **Python 本体に同梱**。単体インストール不要
- `pip install libclang` は `libclang.so` を同梱するが、**Clang 組み込みヘッダ（`stddef.h` 等）は同梱しない**。`clang -print-resource-dir` の引き渡しが別途必要
- jedi は Python **3.10 以上**を要求。libclang 側にバージョン制約は無い
- `dotnet` コマンドの存在は **.NET SDK の存在を意味しない**。`dotnet --list-sdks` で確認すること。「.NET Framework 4.x」は別物
- Ubuntu 24.04 では `dotnet-sdk-8.0` が標準 apt で入る（Microsoft 公式リポジトリ不要）
- WSL に必要なツールは**すべてインストール可能**。ただし Windows 専用コード（`windows.h`、.NET Framework / WPF）は WSL では解析できない
- `.ps1` は **UTF-8 BOM 必須**（PowerShell 5.1 が CP932 として読むため）。`.gitattributes` で `.ps1` は CRLF、`.sh` は LF に固定済み
