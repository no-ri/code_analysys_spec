## 2. 重さの根本原因（これが議論の核心）

フル版が重い原因は一点に集約される。**§4.1 の選定基準1「意味解析（名前解決）を持っているか」**である。

```
正確な名前解決が欲しい
  → コンパイラのフロントエンドが要る (libclang / Roslyn / TypeScript Compiler API)
    → それぞれのランタイムが要る (.NET / Node)
      → ビルドコンテキストが要る (compile_commands.json / .sln / tsconfig.json)
        → 利用者が「ビルドが通る状態」を用意しないといけない  ← 最大の負担
```

### 想定用途との突き合わせ

想定用途は「**初見のソースコードの一次解析の補助**」。嬉しいのは全体像の把握。

| 知りたいこと | 名前解決が要るか |
|---|---|
| どのフォルダに何の機能があるか | 不要 |
| どの辺りが詳細解析を要しそうか | 不要 |
| 規模感・構造の偏り | 不要 |
| モジュール間の大まかな依存 | ほぼ不要（import / include 文を読むだけ） |
| 「この関数の呼び元を漏れなく全部」 | **必要**（ここだけフル版の領分） |

> **見立て（2026-08-26 に合意）**: 一次解析という用途は、フル版の能力のごく一部しか使っていない。したがって名前解決を捨てても用途の大半は満たせる。
> この合意にもとづき E-2 の軸2 = ゼロ（ビルドコンテキストを要求しない）を決めた。
> **ただし実測はまだ無い。** 実プロジェクトでの取りこぼし率は `OPEN_DECISIONS.md` E-3 の「要実測」で確認する。

## 4. 次に議論すること

### E-2（起点）: インストール水準 — **決定済み**

**2軸に分解した。** 当初の表は「利用者のマシンに何を入れさせるか」の1軸しか持っていなかったのが問題だった。

| 軸 | 問い | 結論 |
|---|---|---|
| **軸1** | 利用者の**マシン**に何を入れさせるか | **「軽い」** = Python 3.10+ ＋ `pip install` 1コマンド |
| **軸2** | 利用者に**解析対象**について何を用意させるか | **ゼロ** = ソースツリーが読めればよい |

**軸1の理由**: Python と pip が使えない前提を置くと、解析するための言語処理系から用意する話になり本末転倒。「完全ゼロ」（単一実行ファイル = Go / Rust 実装）は B-2 / B-3 の根拠を無効にするため採らない。オフライン環境では wheel の持ち込みが要る点は既知の穴として受け入れる。

**軸2の理由**: フル版 §7.7 の起動条件（`compile_commands.json` / `.sln` / `tsconfig.json` / 依存入り実行環境）を一つも課さない。「初見のソースコード」は、そもそもビルドが通る状態にあることの方が稀。

**補正（2026-08-26）**: 軸2 = ゼロは**二択ではなく既定値**。追加のソースツリーを外部から渡せる設計にすれば、閉世界の**境界はパラメータになる**（レベル0＝何も渡さない／1＝追加ソースツリー→**定義**まで到達／2＝システムヘッダ→**宣言**まで／3＝ビルドコンテキスト＝フル版）。**レベル1が費用対効果最大**。レベル2は実測で割に合わないと分かった（下記）。

**この決定が実現手段まで確定させる**: 名前解決を持つツール（libclang / Roslyn / TS Compiler API）はビルドコンテキスト無しでは機能しない。したがって軸2 = ゼロは §4.1 の選定基準1 を放棄することと同義であり、**tree-sitter が主力になる**（フル版 §4.7 の格下げを覆す）。

**効果の非対称性**: 軸1を完全ゼロにしても軸2を課せば「まず cmake を通してください」が残る。**効果の大半は軸2にある。**

### E-3: 名前解決を捨てた場合の線引き — **E-2 を受けて具体化済み**

全リストは `OPEN_DECISIONS.md` の E-3 にある。要約すると**4段階**。

| 分類 | 中身 |
|---|---|
| **① 取れる**（`high`） | ディレクトリ構造マップ、規模の偏り、関数・クラス一覧と位置、import/include/using の記述、呼び出し**式**、コメント密度と TODO 分布、命名の語彙集計、分岐数（複雑度の近似）、**Git 変更ホットスポット**、テスト/生成コード/vendor 判別 |
| **②-a 決定的に解ける**（`medium`） | ファイル内の束縛（スコープ解析）、`static` 等ファイルローカルなシンボル、**リポジトリ内で候補が一意な呼び出し**、相対パスで書かれた import/include の解決先 |
| **②-b 名前一致の推測**（`low`） | 粗いコールグラフ（C++ など）、パスで書かれていない依存、継承関係、ソースに書かれた型 |
| **③ 取れない** | 正確なコールグラフ、呼び元の網羅、データフロー、未使用コードの断定、推論された型、マクロ展開後のコード、外部ライブラリのシンボル |

**②-a を新設した理由（2026-08-26）**: 当初②を一括で `low` にしていたが、**推測を含まないものが混ざっていた**。「意味を付ける」作業は6段階あり、**段階の中にも解けるものと解けないものが混在する**。解けるかを決めるのは段階ではなく次の2軸。

| 軸 | 問い |
|---|---|
| **軸A: 情報の所在** | 自ファイル内 / リポジトリ内の他ファイル / **リポジトリ外** |
| **軸B: 名前の一意性** | その言語で名前だけから一意に定まるか（オーバーロード・仮想・動的で崩れる） |

**閉世界仮定**（解析対象のツリーがプログラムの全体）を明示的に置けば、リポジトリ内で候補が一意な呼び出しは**推測ではなく演繹**になる。しかも**仮定の破れは候補数で検出できる**（0個 = `external`、複数 = `ambiguous`）。

**実測1（2026-08-26）**: C の3ファイルを構文木の合成だけで解決した。`b.c` から `a.c` の関数、同名 `static` 2つの分離、`printf` / 未定義関数の外部判定まで**すべて正しく出た。ヘッダ（`a.h`）は解決に不要だった**。

**実測2（同）**: システムヘッダを渡す案（レベル2）を `/usr/include/stdio.h` で試した。**`extern` 宣言 138行に対し、tree-sitter が抽出できた関数宣言は 16件のみ**（ERROR ノード 136）。`__THROW` / `__nonnull` 等の属性マクロで宣言ごと ERROR に落ちる。`printf` はたまたま属性マクロが無く取れただけで、`fprintf` / `sprintf` は取れなかった。**システムヘッダは tree-sitter が最も苦手な入力**。代案として「標準ライブラリの関数名辞書」を持つ方が確実で安い。

詳細は `OPEN_DECISIONS.md` E-3。

**重要な帰結（その1）**: ② の名前一致による結線は §2.3（間違った答えが自信を持って出るツールは有害）の当事者。**L0 では線を引かず** `callee_expr` の文字列だけを出し、名前一致という判断は L2 / L3a の「推測モード」に置く。これは §7.3 のルール1 と一致する — **フル版のために作った層分離が簡易版でそのまま効く。**

**重要な帰結（その2・2026-08-26 の実測から）**: tree-sitter は壊れたコードからも木を返すが、**括弧の不均衡では関数を1つも拾えなくなる**（実測 0/3）。黙って痩せた結果が出るため、**ERROR ノード数を数えて `confidence` に反映する**ことを L0 の必須要件とする。実測の詳細は `OPEN_DECISIONS.md` E-3。

**副産物**: Git 履歴（変更頻度・著者数）は名前解決を一切必要としないのに「どの辺りが詳細解析を要しそうか」に直接効く。**フル版の構想には無い軸**であり、簡易版が単なる下位互換に留まらない可能性がある。→ E-4 の判断材料。

### E-1（次はここ）: 想定用途の再定義

一次解析の補助として、**最小の出力は何か**。E-3 の仕分けが出揃い、**Phase 0 相当の測定も完了した**ので、数字から逆算して決められる状態にある。

#### 測定結果（2026-08-26、[構想] §8.3 の推奨セット。ビルドは一切していない）

| プロジェクト | 言語 | 呼び出し | **②-a** | ②-b | macro | external | ③型解決 | ③間接 |
|---|---|---:|---:|---:|---:|---:|---:|---:|
| cJSON | C | 526 | **66.5%** | 0.0% | 12.4% | 16.2% | 4.9% | 0.0% |
| cmark | C | 1,381 | **59.9%** | 0.0% | 23.2% | 11.4% | 3.5% | 2.0% |
| tinyxml2 | C++ | 909 | **22.2%** | 19.9% | 15.4% | 6.3% | 29.5% | 6.7% |
| requests | Python | 986 | **17.2%** | 2.9% | 0.0% | 40.5% | 39.2% | 0.1% |
| commander.js | JS | 758 | **27.3%** | 0.0% | 0.0% | 7.4% | 64.9% | 0.4% |
| FluentValidation | C# | 1,022 | **5.2%** | 12.3% | 0.0% | 12.8% | 69.1% | 0.6% |

**最大の発見: 言語で桁が違う。E-1 に単一の答えは無い。**

- **C は実質9割が「正体判明」**。②-a 6割 ＋ macro（呼び先のマクロ定義は特定できている）＋ external の中身はほぼ libc（標準ライブラリ辞書でラベル可能）。本当に不明なのは ③ の 5〜7% のみ
- **Python の external 40.5% は大半が builtins**（`isinstance` / `getattr` / `int`）。辞書化で「不明」ではなくなるが ②-a には昇格しない
- **`this.` / `self.` の解決は効く**。commander.js の ②-a 27.3% のうち 24.3% が `this.` 経由
- **C# の 5.2% は過小評価**。メンバ呼び出しの内訳を追加測定したところ `var` はわずか 4.2% で、static 呼び出し 28.1% ＋ 明示型レシーバ 19.2% を実装すれば **35〜40% まで上がる見込み**（ただし到達先の多くはインタフェース宣言であり実装には届かない）
- パースは健全（Python / JS / C# は **ERROR ノード 0**）

#### この測定から出た提案

1. **出力の主役を言語で変える。** C はコールグラフを主役にできる。C++ / C# / Python / JS は構造マップと分布が主役で、コールグラフは `confidence` つきの補助
2. ~~着手順は C から~~ → **初期対象は C と C# の2言語に決定（2026-08-26 指示）**。C だけで進めるとデータセットが C に寄るため。マルチ言語ツールにしたいのでデータは汎用的な形で管理する

詳細と測定方法は `OPEN_DECISIONS.md` E-3。

#### 汎用スキーマの検証（2026-08-26）— **C + C# を選んだ効果が即座に出た**

C の `static`/`extern` と C# の `namespace`/`type` を汎用概念（`kind` / `container_id` / `visibility`）へ写し、cJSON と FluentValidation を**同じ列の SQLite** へ実際に出力した。**列を1つも増やさずに両言語が載った。**

そして **C だけでは気づけない問題が2件露呈した**。

| # | 発見 | C | C# |
|---|---|---:|---:|
| 1 | **シンボルID がシグネチャ無しで衝突し、シンボルが消える** | 2.3% | **17.7%** |
| 2 | **C# の file-scoped namespace（`namespace X;`）を取りこぼす** | — | 名前空間が ID から欠落 |

発見1は §2.3 の「静かな取りこぼし」そのもの。**B-1（SCIP シンボルID）に修正が必要**で、descriptor に**パラメータの型名リスト**を含める（型注釈が無い言語はアリティでフォールバック）。B-1 は「C++ のオーバーロードで要実測」としていたが、**C++ を待たず C# で顕在化した**。

検証スクリプトは `tools/emit-generic-schema.py`。詳細は `OPEN_DECISIONS.md` E-1。

#### ★ コメントを最小の出力に含める（当初案の訂正）

当初案はコメントを「件数だけ」に切り詰めていたが、**一次解析ではコメントが重要**との指摘を受けて実測し、訂正した。

| 項目 | cJSON (C) | cmark (C) | FluentValidation (C#) |
|---|---:|---:|---:|
| **直前に doc コメントを持つ定義** | **34.2%** | **22.6%** | **49.8%** |
| doc コメントの平均長 | 61 文字 | 117 文字 | **239 文字** |
| ファイル先頭コメント | 4 / 4 ファイル | 2 ファイル | **130 / 137 ファイル** |
| マーカー（TODO 等） | 12 | 11 | 10 |

**doc コメントは「この関数が何をするか」を人が書いた唯一の記述で、名前解決を一切必要としない。** 命名の語彙集計より遥かに直接的に「どのフォルダに何の機能があるか」に答える。

**ここは簡易版がフル版と同等以上になりうる唯一の領域**でもある。コンパイラのフロントエンドはコメントを捨てるが（libclang は特別な指定が要り、Roslyn では trivia 扱い）、tree-sitter は comment を第一級ノードとして持つ。

マーカー（TODO / FIXME）は 10〜12件と少なく、**主役は doc コメントの方**だった。

**汎用性の注意**: doc の担い手は言語で違う。C / C# はコメントだが **Python の docstring は文字列リテラル**。`comments` テーブルは「コメント構文」ではなく「**人が書いた説明**」の器として定義する。

## 7. 環境メモ（実測済み・再確認不要）

次セッションで同じ調査を繰り返さないための記録。

- `sqlite3` は **Python 本体に同梱**。単体インストール不要
- `pip install libclang` は `libclang.so` を同梱するが、**Clang 組み込みヘッダ（`stddef.h` 等）は同梱しない**。`clang -print-resource-dir` の引き渡しが別途必要
- jedi は Python **3.10 以上**を要求。libclang 側にバージョン制約は無い
- `dotnet` コマンドの存在は **.NET SDK の存在を意味しない**。`dotnet --list-sdks` で確認すること。「.NET Framework 4.x」は別物
- Ubuntu 24.04 では `dotnet-sdk-8.0` が標準 apt で入る（Microsoft 公式リポジトリ不要）
- WSL に必要なツールは**すべてインストール可能**。ただし Windows 専用コード（`windows.h`、.NET Framework / WPF）は WSL では解析できない
- **tree-sitter（2026-08-26 実測）**: `pip install tree-sitter tree-sitter-language-pack` の**1コマンドで完了。追加依存なし、C コンパイラ不要、計約 7.6MB、371言語対応、対象6言語すべて対応、MIT**。→ **軸1 =「軽い」は成立する**
- **tree-sitter のエラー回復（同上）**: 式の破損・未知のマクロ修飾からは**完全に回復**する（3/3 検出）が、**括弧の不均衡は後続を巻き込んで全滅**する（0/3）。→ ERROR ノード数を `confidence` に反映する設計が必須
- **tree-sitter の速度（同上）**: 1.7MB / 20,000行の C を 0.77 秒。ただし**抽出は S 式クエリで書くこと**（Python 側で木を走査すると 2.37 秒 → クエリなら 0.26 秒、約9倍）
- `.ps1` は **UTF-8 BOM 必須**（PowerShell 5.1 が CP932 として読むため）。`.gitattributes` で `.ps1` は CRLF、`.sh` は LF に固定済み
