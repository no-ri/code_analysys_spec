# ソースコード解析 観点カタログ ＆ 言語別 概念有無マトリクス

**作成日**: 2026-08-09
**目的**: 全言語共通のデータフォーマットを設計するための前段。「理想的に何が分かると嬉しいか」を言語非依存で洗い出し、各言語にその概念が存在するかを整理する
**関連文書**: CODE_ANALYSIS_CONCEPT.md、EXTRACTABLE_DATA_MATRIX.md

---

## 0. この文書の位置づけ

### 前文書との違い（重要）

| 文書 | 問い | 答えの種類 |
|---|---|---|
| EXTRACTABLE_DATA_MATRIX.md | **ツールで取れるか** | ツールの能力 |
| **本文書** | **その言語にその概念が存在するか** | 言語仕様 |

本文書では**ツールの制約を一切考慮しません**。「理想的な解析器があったら何を知りたいか」を先に固定し、そこから逆算してデータ仕様を設計するためです。実装可否は後で突き合わせます。

### 言語列について

**CとC++を分離しました。** 例外・クラス・テンプレート・RAII・名前空間の有無が根本的に異なり、まとめると「C++にはあるがCにはない」情報が消えるためです。実務上も、Cのみのコードベース（組込み等）とC++のコードベースでは必要なスキーマが変わります。

### 記号

| 記号 | 意味 |
|---|---|
| **○** | その言語にその概念が存在する |
| **−** | その言語にその概念が存在しない、または適用対象外 |

境界事例は各表の下に注記します。

## 3.3 設計上の結論

### ① 共通スキーマは想像以上に広く取れる

「言語が違えば全く別のデータが必要」という予想に反し、**中核となる観点の8割前後は全言語共通**です。特に呼び出し関係・データの所在・モジュール依存・変更影響という、当初の目的そのものが完全に共通です。

### ② 分岐は「言語」ではなく「言語グループ」で起きる

分岐軸は5つに整理できます。

| 軸 | 分岐 |
|---|---|
| **手動メモリ管理か GC か** | C / C++ ↔ Python / C# / JS / TS |
| **静的コンパイルか動的実行か** | C / C++ / C# ↔ Python / JS / TS |
| **プリプロセッサの有無** | C / C++ ↔ その他 |
| **静的型付けの強さ** | C / C++ / C# / TS ↔ Python / JS |
| **並行モデル** | 共有メモリ（C / C++ / Python / C#）↔ イベントループ（JS / TS） |

**言語ごとに拡張テーブルを作るのではなく、この5軸に対応する拡張テーブルを作る**のが正しい設計です。C と C++ で `memory_ops` テーブルを共有できます。

### ③ どの言語にも存在しない観点こそ最大の価値

D-13（事前・事後条件）と D-14（不変条件）は、**調査対象の全言語で −** でした。しかしこれらは実務上最も知りたい情報です。

- 「この関数は必ずロック取得後に呼ぶこと」
- 「この構造体のこのメンバは初期化関数を経由せずに触ってはいけない」
- 「モジュールAからモジュールBを直接呼んではいけない」

**言語が表現手段を持たないから、既製ツールにも入っていない。** ここを自作データセットの上で表現できるようにすれば、それが差別化になります。

→ スキーマに **`constraints` テーブル**（人が書いたルールを保持）を用意し、`findings` と接続する設計を検討すべきです。これは抽出ではなく宣言なので、L0（抽出層）ではなく別系統として扱います。

### ④ 「−」は空欄ではなく明示的に記録する

ある言語で概念が存在しない場合、`NULL` ではなく **`not_applicable`** として記録すべきです。「調べていない」「取れなかった」「そもそも存在しない」の3つは意味が全く違い、混ぜると解析結果を誤読します。

```
status: resolved | unresolved | not_applicable | not_extracted
```

**採用済み**（2026-08-25）。当初 CODE_ANALYSIS_CONCEPT.md §3.1 が持っていた `resolution` 列（`via_function_pointer` 等の理由分類）と語彙が衝突していたため、
**`status`（状態）と `reason`（理由）の2列に分離**して両方を残す形で決着しました。
併せて「解決できたと言っているが、どれだけ信じてよいか」を表す `confidence`（`high` / `medium` / `low`）列を追加しています。

→ 決定の根拠は CODE_ANALYSIS_CONCEPT.md §3.1.1 / §3.1.2 を参照。

### ⑤ 次のステップ

本文書（理想）と EXTRACTABLE_DATA_MATRIX.md（現実）を突き合わせることで、

- **理想 ○ ／ 現実 ○** → 初版で実装
- **理想 ○ ／ 現実 △** → `confidence` 列つきで実装
- **理想 ○ ／ 現実 ×** → スキーマには列を用意し、当面は空にする
- **理想 − ／ 現実 −** → 該当言語では `not_applicable`

という4象限に整理できます。**3番目（列は用意するが埋めない）が将来の拡張性を担保する部分**であり、本文書を先に作った理由です。
