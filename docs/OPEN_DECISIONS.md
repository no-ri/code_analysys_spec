### [2026-08-25] A-1. `resolution` の値セット — **`status` と `reason` の2列に分離**

1列に「解決できたか」と「なぜできなかったか」という粒度の異なる2軸が同居していたのが原因。分離して両方を残す。

| 列 | 問い | 値 |
|---|---|---|
| `status` | どの状態か | `resolved` / `unresolved` / `not_applicable` / `not_extracted` |
| `reason` | なぜ解決できなかったか（`status = unresolved` のときのみ） | `via_function_pointer` / `virtual_unresolved` / `macro_expanded` / `unknown` |

**採用理由**: §7.3 のフィルタ原則が `WHERE status = 'resolved'` と素直に書ける。`reason` に値を追加しても `status` の値域が汚れず既存クエリが壊れない。「未対応の言語だから空」と「その言語に概念が無いから空」が区別できる。

**記載先**: [構想] §3.1 / §3.1.1 / §3.3、[理想] §3.3 ④（採用済みと追記）、[現実] §「初版スキーマ」

### [2026-08-25] A-2. `confidence` 列 — **`high` / `medium` / `low` の enum で追加**

§7.4-2 が必須としていた信頼度列を全テーブルに追加。数値（0.0〜1.0）は採らない。

**採用理由**: libclang も Jedi も確率値を返さないため、数値にすると根拠のない小数を書くことになり、§2.3 の「間違った答えが自信を持って出てくるツールは有害」に逆行する。enum なら抽出器が根拠を持って言える粒度に一致する。

`status`（解決できたか＝事実）/ `reason`（できなかった理由＝事実）/ `confidence`（どれだけ信じてよいか＝判断）は役割が重複しない。Python の解決結果は `status = resolved` かつ `confidence = low` になる。

**記載先**: [構想] §3.1 / §3.1.2

### [2026-08-25] A-3. `lang` / `extractor` / `snapshot` の適用範囲 — **全テーブルに持たせる**

`symbols` から JOIN で引く案は、未解決の行（`callee_id` が空）で対応先が無く、抽出器のバージョンだけを上げて再抽出したケースでも破綻するため却下。

L0 の中間ファイルではメタ情報行に1回だけ書き、L1 取り込み時に各行へ展開する。**冗長になるのは L1 のみ**で、手書きする中間ファイル側は冗長にならない。

**記載先**: [構想] §3.1 / §3.1.3 / §7.6

### [2026-08-25] B-1. SCIP シンボルIDのマッピング規則 — **`local` スキームを定義**

SCIP の `<scheme> <package-manager> <package-name> <version> <descriptor...>` のうち、C/C++ にはパッケージ座標に相当する概念が無いことが問題だった。

自リポジトリのコードは `local <repo-name> <snapshot> <descriptor...>`、外部ライブラリは `scip-python` / `scip-typescript` が出す本来の座標（`pypi requests 2.31.0` 等）をそのまま受け入れる。両者は同じ名前空間に共存する。

**要実測（Phase 0）**: descriptor を各言語のネイティブIDから機械的に生成できるか。特に C++ のオーバーロード・テンプレート。

**記載先**: [構想] §3.2.1

### [2026-08-25] B-2. L1 のストア実体 — **SQLite（`facts/db.sqlite`）**

追加依存ゼロ（Python 本体に同梱）、単一ファイルで可搬、中身を直接覗ける、DuckDB / Parquet への移行も容易、という理由。TSV のみ・DuckDB・Parquet・グラフDB は却下。

**記載先**: [構想] §3.4.1

### [2026-08-25] B-3. 実装構成 — **独立プロセス + GUI 後付けのための3つの約束**

Roslyn（.NET）も ts-morph（Node）も別ランタイムでしか動かないため、抽出器は subprocess として起動する。接点は TSV ファイルのみ。終了コードで「対象ファイルなし（正常）」と「ビルドコンテキスト不足」「異常」を区別し、§7.7 の言語ごと独立を成立させる。

GUI は初版で作らないが、① ロジックを `core/` に置き CLI を薄くする ② ジョブ設定ファイル（TOML）を用意する ③ 進捗を構造化出力する、の3点を初版から守る。将来の GUI はローカル Web UI を想定（L3a 可視化層と同じ土俵に乗るため）。

**記載先**: [構想] §9.1 / §9.2

### [2026-08-25] B-4. `snapshot` の粒度 — **`git describe --always --dirty` 相当**

`8f3ac21` / `8f3ac21-dirty` / `nogit-20260825T143052`。`-dirty` は「このファクトデータは再現不能」を明示するためのもので、§2.3 の「不確かさを黙って隠さない」思想に沿う。ブランチ名は識別子として不安定なため含めない。

**記載先**: [構想] §3.4.2
