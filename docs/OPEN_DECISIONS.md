#### ① 取れる（`confidence = high`）— 構文と位置だけで決まるもの

| 出力 | 中身 | 手段 |
|---|---|---|
| ディレクトリ構造マップ | パス階層、ファイル数、行数、拡張子別の言語構成 | ファイル走査のみ。tree-sitter すら不要 |

| テスト／生成コード／vendor の判別 | パス規約と生成物マーカーによる分類 | ヒューリスティック。誤分類は起きるので `confidence = medium` 相当 |

#### ② 取れるが近似（`confidence = low`）— 名前の一致による推測が入るもの

| 出力 | 何をするか | 何が解けないか |
|---|---|---|
| モジュール間の依存図 | `import` 文の解決先をリポジトリ内ファイルに**名前一致で**当てる | 相対 import、path alias、`#include` のインクルードパス。外部パッケージは名前だけ残る |
| 粗いコールグラフ | `callee_expr` の識別子部分と関数名の一致で線を引く | 同名関数、オーバーロード、メソッド名の衝突を区別できない |
| 継承・実装関係 | `class Foo : Bar` の `Bar` を名前で当てる | どの `Bar` か（名前空間・同名クラス）は解けない |
| 宣言された型 | 型注釈・型名が**ソースに書いてあれば**文字列として拾う | 推論された型（`var` / `auto` / 注釈なし Python / TS の推論）は取れない |

**② の扱いに関する重要な帰結**（[構想] §2.3・§7.3 との整合）:

§2.3 は「**間違った答えが自信を持って出てくるツールは、答えが出ないツールより有害**」と決めている。名前一致による結線はまさにこのリスクの当事者であり、**L0（抽出層）では線を引かない**。L0 が出すのは事実（`callee_expr` の文字列）だけで、名前一致という**判断**は L2 / L3a 側に置き、利用者が明示的に有効化する「推測モード」として扱う。

これは §7.3 のルール1「L0 に判断ロジックを一切入れない」と一致する。**フル版のために作った層分離が、簡易版でそのまま効く。**

- 正確なコールグラフ（仮想呼び出し、関数ポインタ、デリゲート、動的ディスパッチ）
- 「この関数の呼び元を漏れなく全部」
- 変数の読み書き箇所の網羅（データフロー）
- 未使用コードの断定
- 推論された型
- マクロ展開後のコード、条件コンパイルの有効枝（tree-sitter は `#ifdef` の内外を**両方**構文木に載せる。[構想] §4.7 の注意）

- リフレクション・動的呼び出し（`getattr` / `Type.GetMethod` / `eval`）※**フル版でも解けない**
- 言語をまたぐ呼び出し（FFI）※**フル版でも非スコープ**（D-6）

### [2026-08-26] E-2. インストール水準 — **2軸に分解。軸1 =「軽い」／軸2 = ゼロ**

当初の E-2 は「利用者のマシンに何を入れさせるか」という**1軸しか持っていなかった**。実際にはもう1軸ある。

| 軸 | 問い | 対象 |
|---|---|---|
| **軸1** | 利用者の**マシン**に何を入れさせるか | ツール側 |
| **軸2** | 利用者に**解析対象**について何を用意させるか | 対象リポジトリ側 |

#### 軸1 = 「軽い」（Python 3.10+ ＋ `pip install` 1コマンド）

**採用理由**: Python と pip が使えない前提を置くと、解析するための言語処理系から用意する話になり本末転倒。開発者のマシンに Python が無いケースは想定しない。

「完全ゼロ」（単一実行ファイル）を採らない理由: Go / Rust での実装を意味し、**B-2**（ストアは SQLite ＝ Python 本体同梱だから追加依存ゼロ）と **B-3**（ローダーは Python）の根拠がまるごと無効になる。tree-sitter 本体は C なので Go / Rust からも使えるが、実装言語の選び直しは既存の決定を再利用できなくする。配布の手間に対して失うものが大きい。

**受け入れる制約**: オフラインの閉じた環境では wheel の持ち込みが必要。これは既知の穴として受け入れる。

#### 軸2 = ゼロ（ビルドコンテキストを要求しない）

要求するのは「**ソースツリーが読める状態にあること**」だけ。[構想] §7.7 が抽出器の起動条件として挙げていたもの（`compile_commands.json` / `.sln`・`.csproj` / `tsconfig.json` ＋ `node_modules` / 依存パッケージの入った実行環境）を**一つも課さない**。

**採用理由**: 想定用途は「初見のソースコードの一次解析」であり、**その状況でビルドが通る状態にあることの方が稀**。ビルドが通らないリポジトリ、依存を落とせない環境、zip を展開しただけのツリー、受け取った一部だけのソース — これらが全部そのまま対象になる。

#### この2軸のうち、実現手段を確定させるのは軸2

名前解決を行うツール（libclang / Roslyn / TypeScript Compiler API）は**ビルドコンテキスト無しでは機能しない**（プロセスは動くが型が解決できない）。したがって軸2 = ゼロは、**[構想] §4.1 の選定基準1（意味解析を持っているか）を放棄する**ことと同義であり、使える手段は構文解析までに絞られる。

→ **tree-sitter が主力になる。** [構想] §4.7 はこれを「まだ抽出器を書いていない言語の暫定対応」と格下げしているが、**簡易版ではこの位置づけを覆す**。

#### 効果の非対称性（軸1から詰めてはいけない理由）

軸1を「完全ゼロ」にしても、軸2を課せば「まず cmake を通してください」が残るので利用者の負担は消えない。逆に軸1が「軽い」でも軸2がゼロなら、体験は **clone → 1コマンド → 結果が出る** になる。**効果の大半は軸2にある。**

軸1から議論すると実装言語の選定に入ってしまい、用途の話に戻れなくなる。順序として軸2を先に確定させた。

**記載先**: 本ファイル E-3（この決定を前提とした線引き）。E-1 / E-4 の決定後、簡易版の構想文書へ移す

### [2026-08-25] A-1. `resolution` の値セット — **`status` と `reason` の2列に分離**

1列に「解決できたか」と「なぜできなかったか」という粒度の異なる2軸が同居していたのが原因。分離して両方を残す。

| 列 | 問い | 値 |
|---|---|---|
| `status` | どの状態か | `resolved` / `unresolved` / `not_applicable` / `not_extracted` |
| `reason` | なぜ解決できなかったか（`status = unresolved` のときのみ） | `via_function_pointer` / `virtual_unresolved` / `macro_expanded` / `unknown` |

**採用理由**: §7.3 のフィルタ原則が `WHERE status = 'resolved'` と素直に書ける。`reason` に値を追加しても `status` の値域が汚れず既存クエリが壊れない。「未対応の言語だから空」と「その言語に概念が無いから空」が区別できる。

**記載先**: [構想] §3.1 / §3.1.1 / §3.3、[理想] §3.3 ④（採用済みと追記）、[現実] §「初版スキーマ」

### [2026-08-25] A-2. `confidence` 列 — **`high` / `medium` / `low` の enum で追加**

§7.4-2 が必須としていた信頼度列を全テーブルに追加。数値（0.0〜1.0）は採らない。

**採用理由**: libclang も Jedi も確率値を返さないため、数値にすると根拠のない小数を書くことになり、§2.3 の「間違った答えが自信を持って出てくるツールは有害」に逆行する。enum なら抽出器が根拠を持って言える粒度に一致する。

`status`（解決できたか＝事実）/ `reason`（できなかった理由＝事実）/ `confidence`（どれだけ信じてよいか＝判断）は役割が重複しない。Python の解決結果は `status = resolved` かつ `confidence = low` になる。

**記載先**: [構想] §3.1 / §3.1.2
