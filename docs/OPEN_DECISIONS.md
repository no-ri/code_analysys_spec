### E-1. 想定用途の再定義 — **決定済み（2026-08-26）**

**初見のソースコードの一次解析の補助**。知りたいのは全体像。

- どの辺りが詳細解析を要しそうか

**決めること**: この用途を満たす最小の出力は何か。フル版 §1.1 の目的（正確なコール関係・データの所在）とどう関係するか（置き換えか、部分集合か、別物か）。

#### 初期対象言語 — **C と C#（2026-08-26 指示）**

E-3 の測定では C が最も価値が出たが、**C だけで進めるとデータセットが C に寄る**。マルチ言語ツールにしたいので、データは汎用的な形で管理する。

**この2つは C 系言語の中で互いに最も遠く、スキーマの一般性を検証するペアとして最適。**

| | C | C# |
|---|---|---|
| 名前の入れ物 | ファイル（翻訳単位） | 名前空間 → 型 |
| メソッドの所有者 | 無い | 型 |
| 可視性の仕組み | リンケージ（`static` / `extern`） | アクセシビリティ（`public` / `internal` / …） |
| 前処理 | マクロあり | 無し |
| 呼び出しの主形 | 直接（②-a 6割） | メンバ（③型解決 7割） |

**片方で通って片方で破綻する設計は、この2つを並べれば露呈する。** 実際に露呈した（下記）。

#### 汎用スキーマ案（言語固有概念を列に持ち込まない）

C の `static` / `extern` や C# の `namespace` / `type` を**そのまま列にすると C 専用・C# 専用の表になる**。共通の問いへ写す。

| 汎用概念 | 問い | C での対応 | C# での対応 |
|---|---|---|---|
| **`kind`** | 何であるか | `function` / `macro` / `file` | `method` / `type` / `namespace` / `file` |
| **`container_id`** | 何の中にあるか（入れ子の親） | ファイル | 名前空間 → 型 |
| **`visibility`** | 名前がどこまで見えるか | `extern`→`public` / `static`→`module` | `public`→`public` / `internal`→`module` / `private`・`protected`→`private` |
| **`refs.kind`** | どんな関係か | `call` / `import`(`#include`) | `call` / `import`(`using`) |
| **`refs.reason`** | なぜ解けないか | `external` / `ambiguous` / `macro_expanded` / `via_function_pointer` | `external` / `ambiguous` / **`needs_type`** |

**言語に無い概念は「行が出ない」だけで、列は共通のまま。** C に `private` が無く、C# に `macro` が無いのは、A-1 が `not_applicable` で扱おうとしていたものと同じ形。

##### `refs.reason` の値域（提案）

A-1 が定めた4値に、簡易版で必要になる3値を足す。**`reason` に値を追加しても `status` の値域が汚れない**という A-1 の設計意図どおりの拡張。

| 値 | 意味 | 出典 |
|---|---|---|
| `external` | 定義がリポジトリ外（閉世界の境界の外） | **新設**（E-3） |
| `ambiguous` | リポジトリ内の候補が複数。名前だけでは決まらない | **新設**（E-3） |
| **`needs_type`** | **メンバ呼び出しで、レシーバの型が分からないため解けない** | **新設**（E-1） |
| `via_function_pointer` | 関数ポインタ／デリゲート経由 | A-1 |
| `virtual_unresolved` | 仮想ディスパッチ | A-1 |
| `macro_expanded` | マクロ経由 | A-1 |
| `unknown` | 上記のいずれでもない | A-1 |

**`needs_type` を `unknown` に混ぜてはいけない理由**: C# の呼び出しの **69% がこれ**。混ぜると最大の分類が「理由不明」になり、「**型解決さえあれば解ける**」という情報が消える。`external`（境界を広げれば解ける）／`ambiguous`（名前の一意性の問題）とも性質が違い、**何を足せば解けるようになるか**が値ごとに違う。

```
refs: src_id=...  dst_id=NULL  dst_expr="_validator.Validate"
      status=unresolved  reason=needs_type  confidence=low
```

#### ★ 発見1: シンボルID がシグネチャ無しでは衝突する（B-1 の要修正）

| プロジェクト | 生成した symbol | ユニーク ID | **衝突で消える** |
|---|---:|---:|---:|
| cJSON（C） | 175 | 171 | **4 件（2.3%）** |
| FluentValidation（C#） | 916 | 754 | **162 件（17.7%）** |

C# の消失例（いずれもオーバーロード）:

```
x6  DefaultValidatorExtensions#Matches().
x6  DefaultValidatorExtensions#LessThan().
x6  DefaultValidatorExtensions#GreaterThan().
```

**これは §2.3 の「静かな取りこぼし」そのもの。** 図は綺麗に出るが 17.7% のシンボルが存在しないことになる。

**C だけで進めていたら気づけなかった**（C は 2.3%、しかも中身は `#ifdef` の枝ごとに5回定義された同一マクロで、原因が別）。

> **B-1 への修正提案**: descriptor に**パラメータの型名リスト**を含める。B-1 は「要実測（Phase 0）: descriptor を機械的に生成できるか。特に C++ のオーバーロード」と書いていたが、**C# でも同じ問題が起きることが実測された**。
> 型名はソースに書いてあるので取得できる（C# の `var` は引数には現れない）。型注釈が無い言語（Python / JS）は**アリティ（引数の個数）**でフォールバックする。
> 出現順の連番は編集で変わるため採らない（B-4 が「ブランチ名は識別子として不安定」を退けたのと同じ理由）。

#### ★ 発見2: C# の file-scoped namespace を取りこぼしていた

FluentValidation は `namespace FluentValidation;`（C# 10 以降の file-scoped 形式）を使っており、`namespace_declaration`（ブロック形式）しか見ていない実装では**名前空間が ID から丸ごと欠落する**。

**言語仕様の新旧2形式は、tree-sitter では別ノード型になる。** §2.3 の「長い尻尾の言語仕様」が最初の1言語で早速出た。実装時のチェック項目とする。

#### ★ コメントは最小に含める（2026-08-26、当初案の訂正）

**当初案はコメントを「件数だけ」に切り詰めていた。これは誤りだった。** 一次解析ではコメントが重要な情報であるとの指摘を受けて実測した。

| 項目 | cJSON (C) | cmark (C) | FluentValidation (C#) |
|---|---:|---:|---:|
| コメント総数 | 403 | 620 | 4,804 |
| 定義の総数 | 184 | 394 | 999 |
| **直前に doc コメントを持つ定義** | **34.2%** | **22.6%** | **49.8%** |
| doc コメントの平均長 | 61 文字 | 117 文字 | **239 文字** |
| ファイル先頭コメント | 4 / 4 ファイル | 2 ファイル | **130 / 137 ファイル** |
| マーカー（TODO 等） | 12 | 11 | 10 |
| コメントアウト疑い | 0 | 5 | 146 |

**doc コメントは「この関数が何をするか」を人が書いた唯一の記述であり、名前解決を一切必要としない。** C# では定義の半分に付いていて平均 239 文字。一次解析の用途（どのフォルダに何の機能があるか）に対して、**命名の語彙集計よりも遥かに直接的な答え**になる。

> **さらに重要**: ここは**簡易版がフル版と同等以上になりうる唯一の領域**。コンパイラのフロントエンドはコメントを捨てる（libclang は保持に特別な指定が要り、Roslyn では trivia 扱い）。tree-sitter は comment を第一級ノードとして持つ。

**マーカー（TODO / FIXME）は思ったより少なかった**（10〜12件）。E-3 の①で「未整理そうな領域の当たり」として挙げていたが、**主役は doc コメントの方**だと分かった。

##### confidence の規則（実測に基づく）

| コメントの形 | cJSON | FluentValidation | `confidence` |
|---|---:|---:|---|
| `///`（C# XML doc） | — | **54.3%** | **`high`**（明示的な doc 記法） |
| `/**`（doc ブロック） | 0% | — | **`high`** |
| `/* */` 通常ブロック | **100%** | — | `medium`（隣接規則のみ） |
| `//` 通常行 | — | 45.7% | `medium` |

**明示的な doc 記法があれば `high`、隣接だけなら `medium`。** 「直前のコメントは doc である」は慣習に基づく判断なので、**位置は事実として必ず記録し、紐付けは confidence つきで別に持つ**（L3a で再計算できる）。

##### 汎用性の確認（C 専用にしない）

**doc の担い手は言語で違う。** C / C# ではコメントだが、**Python の docstring はコメントではなく文字列リテラル**（関数本体の最初の式）。`comments` テーブルは「コメント構文」ではなく「**人が書いた説明**」を入れる器として定義し、Python の docstring も同じテーブルに `kind = doc` で入れる。

#### ★ 他言語で空く軸の先行確認（2026-08-26）

**初期対象は C + C# のまま変えない**が、**列の定義**にだけ影響する軸が他言語にある。列はあとから変えるとデータの作り直しになる（A-3 と同じ構造）ので、**「そういう形がある」ことだけ先に確認**した。抽出器の実装は第2段でよい。

##### 実測: 3つの軸が空いている

| 軸 | C | C# | JS | Python | C+C# でカバー |
|---|---:|---:|---:|---:|---|
| **無名関数の中の呼び出し** | 0.0% | **9.1%** | **31.3%** | 0.0% | **部分的** |
| **doc を持つ定義**（docstring 含む） | 34.2%（comment） | 49.8%（comment） | — | **65.0%（文字列リテラル）** | **×** |
| **visibility の決まり方** | 宣言の修飾子 | 宣言の修飾子 | **修飾子型14 + リスト型3 の混在** | 慣習（`_foo`）+ `__all__` | **×** |

（requests はモジュール docstring も 19 ファイル中 15（79%）が持つ。comment ノード 532 件には **docstring は一切含まれない**。）

##### 軸1: 無名関数 — **C# で既に 9.1%。JS では 31.3%**

C# の `RuleFor(x => x.Surname)` のようなラムダの中にも呼び出しがある。**C だけを見ていたら 0% なので存在にすら気づかない。**

**設計判断**: 無名関数を `symbols` に登録すると **ID を位置ベースにするしかなく、B-4 が退けた「不安定な識別子」になる**。

> **採る案**: 無名関数は `symbols` に登録しない。`refs.src_id` は**囲む名前つき関数**にする。ただし `refs` に **`via_lambda`**（またはネスト深さ）を持たせ、「ラムダ内からの呼び出し」と分かるようにする。
> ID の不安定さを避けつつ情報も失わない。JS の 31.3% も「この関数の中のコールバックから呼ばれている」として残る。

##### 軸2: doc の担い手 — Python は**コメントではない**

requests の定義の **65.0%** が docstring を持つが、**`comment` ノードには一切入らない**（文字列リテラル）。

> **採る案**: `comments` テーブルに **`source_kind`** 列（`comment` / `string_literal`）を持たせる。テーブルは「コメント構文」ではなく「**人が書いた説明**」の器として定義する（E-1 で既に方針として書いたものを、列として具体化）。

##### 軸3: visibility の由来 — 3種類ある

C も C# も**宣言に修飾子が付く**形しかない。他言語には別の形がある。

| 由来 | 例 | `confidence` |
|---|---|---|
| `declaration` | C の `static`/`extern`、C# の `public`、JS の `export const` | `high` |
| `export_list` | JS の `export { A, B }`、Python の `__all__` | `high`（ただし**宣言箇所とは別の場所を読む必要がある**） |
| `convention` | Python の `_foo`、Go の先頭大文字 | **`medium` / `low`** |

**commander.js は同じファイル内に修飾子型14箇所とリスト型3箇所が混在していた。** 「言語ごとにどちらか」ではなく「**同じ言語に両方ある**」。

> **採る案**: `symbols` に **`visibility_source`** 列（`declaration` / `export_list` / `convention` / `linkage`）を持たせる。C と C# は常に `declaration`（または `linkage`）で `confidence = high`。慣習型が来たときに `confidence` を下げられる。

##### 今やらないこと

Go / Rust / Java は上記3軸の**亜種**にしかならない見込み（Go の先頭大文字＝`convention`、Rust の `pub`＝`declaration`、`mod`＝`container` の変種）。**第2段でよい。**
各言語の抽出器の設計も第2段。**今回は列定義への反映のみ。**

#### 解決の階段と、解けるかを決める2軸（2026-08-26 追記）

##### 意味を付ける6段階

| 段階 | やること | 必要な入力 | 軸2 = ゼロで可能か |
|---|---|---|---|
| 1 | **スコープ解析**（識別子がどの束縛を指すか） | そのファイルの木 ＋ 言語のスコープ規則 | **○ 完全に可能** |
| 2 | **モジュール解決**（import / include 先の特定） | 検索パス、パッケージ境界 | **△ 混在**（下記） |
| 3 | **エクスポート面の解析**（対象ファイルの定義表） | 対象ファイルの木（再エクスポートは推移的） | 2 次第 |
| 4 | **シンボルID の付与** | 1〜3 | 2 次第 |

| 6 | **オーバーロード解決・仮想ディスパッチ** | 5 ＋ 言語規則 | **× 不可** |

段階1は**追加入力ゼロで到達できる**。Python は標準 `symtable` が無料で行う（実測）。他5言語は tree-sitter の木の上に自作する。

##### 解けるかを決めるのは段階ではなく、この2軸

| 軸 | 問い | 値 |
|---|---|---|
| **軸A: 情報の所在** | 答えを出すのに必要な情報はどこにあるか | 自ファイル内 / **リポジトリ内の他ファイル** / リポジトリ外 |
| **軸B: 名前の一意性** | その言語で、名前だけから一意に定まるか | 定まる / 定まらない（オーバーロード・仮想・動的） |

**両方が満たされたときだけ解ける。** 段階2の中に解けるものと解けないものが混在するのは、段階2が軸Aの3値すべてにまたがっているため。

| 例 | 軸A | 軸B | 結果 |
|---|---|---|---|
| C: `b.c` から `a.c` の `compute()` を呼ぶ | リポジトリ内 | ○ | **解ける** |
| C: `printf()` | リポジトリ外 | ○ | 解けない（`external`） |
| C++: オーバーロードされた `f(x)` | リポジトリ内 | **×** | 解けない（段階5が要る） |
| 任意: `obj.method()` | リポジトリ内 | × | 解けない（段階5が要る） |

##### 閉世界仮定 — 推測ではなく「仮定つきの演繹」にできる

**解析対象のソースツリーがプログラムの全体である**、という仮定を明示的に置く。この仮定の下では、リポジトリ内で候補が一意に定まる呼び出しは**推測ではなく演繹**になる。

そして**仮定が破れた箇所は検出できる**。候補数が答えを教える。

| リポジトリ内の候補数 | 意味 | `status` / `reason`（A-1） |
|---|---|---|
| **1個** | 閉世界仮定の下で一意 | `resolved` |
| **0個** | 定義がリポジトリ外にある（外部ライブラリ等） | `unresolved` / **`external`** |
| **2個以上** | 名前だけでは決まらない | `unresolved` / **`ambiguous`** |

**A-1 への拡張提案**: `reason` に **`external`** と **`ambiguous`** を追加する。A-1 は「`reason` に値を追加しても `status` の値域が汚れず既存クエリが壊れない」ことを採用理由に挙げており、この拡張はその設計意図どおりの使い方になる。

##### 実測: C の3ファイルを構文木の合成だけで解決した（2026-08-26）

`a.h`（宣言）/ `a.c`（`compute` と `static helper` を定義）/ `b.c`（`main` と別の `static helper` を定義し、`compute` / `printf` / `log_msg` を呼ぶ）を tree-sitter で解析し、定義表を合成して解決した結果。

| 呼び出し | 結果 |
|---|---|
| `a.c:3` `compute` → `helper` | **resolved** → `a.c:2`（同一ファイルの static が優先） |
| `b.c:5` `main` → `helper` | **resolved** → `b.c:3`（同上。**同名 static が2つあっても正しく分離できた**） |
| `b.c:5` `main` → `compute` | **resolved** → `a.c:3`（リポジトリ内で外部リンケージ定義が一意） |
| `b.c:5` `main` → `printf` | unresolved / `external` |
| `b.c:6` `main` → `log_msg` | unresolved / `external`（宣言だけあり定義なし） |

**`a.h` は解決に不要だった。** C は名前修飾が無く、外部リンケージのシンボルはプログラム全体で一意でなければならないため、**リポジトリ内の全定義を集めるだけで決まる**。ヘッダは裏付けにしかならない。

**破れる条件**（＝ `confidence` を下げる／`ambiguous` にする条件）: マクロで生成された関数名、条件コンパイルで定義が分岐している、ビルドから除外されたファイルに同名定義がある、関数ポインタ経由。

##### 閉世界の境界は二択ではなく「つまみ」（2026-08-26 追記）

手持ちに無いファイルを**外部から渡せる設計**にすれば、その分だけ解決が進む。処理は同じで、**渡されたソースを定義表に足すだけ**。新しい機構は要らない。

つまり **軸2 = ゼロは二択ではなく既定値**であり、閉世界の**境界がパラメータ**になる。

| レベル | 渡すもの | 得られるもの | 追加要求 |
|---|---|---|---|
| **0**（既定） | 何も渡さない | リポジトリ内で閉じるものだけ | なし |
| **1** | **追加のソースツリー**（別リポジトリの社内共通ライブラリ等） | **定義**まで到達。②-a がそのまま広がる | ソースツリーのパス1つ |
| **2** | システムヘッダ / SDK のヘッダ | **宣言**まで（定義は無い） | ヘッダのパス（実質インクルードパス） |
| **3** | ビルドコンテキスト | フル版 | フル版の要求 |

**レベル1と2は得られるものが質的に違う。** レベル2で得られる `printf` は `is_definition = false` の行き止まりになる。これは §7.7 の `[DllImport]` について既に設計済みの「切れた線」と同じ形で、コールグラフはそこで止まる（そしてそれが正しい）。シグネチャが分かり「これは自分たちのコードではない」と断定できる点に価値がある。

##### 実測: `stdio.h` を渡してみた（2026-08-26）— レベル2は割に合わない

| 項目 | 実測値 |
|---|---|
| ファイル | 34,649 バイト / 985 行 |
| **ERROR ノード** | **136** |
| `extern` 宣言の行数（grep） | **138** |
| **tree-sitter が抽出できた関数宣言** | **16**（ユニーク13） |
| `printf` | **取れた**（L363） |
| `fprintf` / `sprintf` / `snprintf` | **取れなかった** |

原因はマクロ。

```c
extern int printf (const char *__restrict __format, ...);              // 取れた
extern int fprintf (FILE *__restrict __stream, ...) __nonnull ((1));   // 取れない
extern int sprintf (char *__restrict __s, ...) __THROWNL;              // 取れない
```

`__THROW` / `__nonnull` / `__wur` / `__REDIRECT_NTH` を未知トークンとして扱い、宣言ごと ERROR に落とす。`printf` はたまたま属性マクロが付いていなかったから取れただけ。

さらに `stdio.h` 自身が **18個のヘッダを include** していた。1ファイル渡せば済む話ではなく、結局インクルードパスを渡すことになる＝軸2 = ゼロの放棄。

> **システムヘッダは tree-sitter が最も苦手とする入力である。** マクロ密度が実コードより遥かに高いため。

##### 代案: 標準ライブラリの関数名辞書

「`printf` は libc の関数だ」と言いたいだけなら、ヘッダをパースするより**名前の辞書を持つ**方が確実で安い。C89 / C99 / POSIX の関数名は数百件の静的データで済み、パース失敗の影響を受けない。同じ発想が他言語にも効く（Python の builtins と標準ライブラリ名、C# の BCL 主要名前空間、Node の組み込みモジュール）。

**`external` を「未知の外部」と「既知の標準ライブラリ」に分けられれば、一次解析には十分。**

##### 設計への反映

1. **境界をデータに持つ**。「解けなかった」ではなく「**この境界の外だから解けなかった**」と言えるようにする。境界を広げれば解けるものが増える、という関係が利用者から見える
2. **B-1 の `local <repo-name>` スキームがそのまま効く**。追加ソースツリーは別の repo-name を持てばよい
3. **新しい前提が1つ増える**: レベル2 を採る場合、**渡されたヘッダが実際のビルドで使われたものと同じ保証は無い**。バージョン違いのヘッダは誤った解決を生む。閉世界仮定と並べて明示・記録する
4. **境界を広げるのは既定にしない**。`external` のまま残った呼び出しの集計は「**このプロジェクトが依存する外部 API の一覧**」であり、一次解析では有用な出力。広げるとこの情報が失われるため、**目的に応じて利用者が選ぶつまみ**とする

##### 言語別: リポジトリ内解決の強さ

| 言語 | 強さ | 理由 |
|---|---|---|
| **C** | **強** | 名前修飾なし・オーバーロードなし。外部リンケージは全体で一意。`static` はファイル内で閉じる |
| **C#** | **強** | 名前空間 ＋ `using` が宣言されており、同一アセンブリ内は全ファイルの型宣言を集めれば決まる。ただしオーバーロードは段階5が要る |
| **Python** | 中 | import 先がパスで書いてある。動的要素（`getattr` / 条件 import / `sys.path` 操作）が破れ要因 |
| **TS/JS** | 中 | 相対パスは書いてあるが、拡張子省略・`index` 解決・`paths` / `baseUrl` が曖昧要因 |
| **C++** | **弱** | 情報がリポジトリ内に全部あっても、名前空間 ＋ オーバーロード ＋ ADL ＋ テンプレートで**名前だけでは決まらない**（軸B が × ） |

**C++ が弱いのは情報の所在ではなく言語規則の問題**。軸A と軸B が独立であることの実例。

#### ① 取れる（`confidence = high`）— 構文と位置だけで決まるもの

| 出力 | 中身 | 手段 |
|---|---|---|
| ディレクトリ構造マップ | パス階層、ファイル数、行数、拡張子別の言語構成 | ファイル走査のみ。tree-sitter すら不要 |
| 規模の偏り | フォルダ／ファイル別の行数分布、上位 N | 同上 |
| 関数・クラス・メソッドの一覧と位置 | `name` / `kind` / `file` / `start_line` / `end_line` | tree-sitter の構文ノード。[構想] §3.1 の `symbols` にそのまま入る |
| `import` / `include` / `using` の**記述** | 文そのものとその位置 | 構文ノード。※**解決先**は ② |
| 呼び出し**式**の一覧 | `caller_id`（囲っている関数）、`callee_expr`（式のテキスト）、位置 | `calls` の `callee_id` を空にした行（A-1 の `status = unresolved`） |
| コメントとその密度 | コメント行数／コード行数、`TODO` / `FIXME` / `HACK` の位置 | tree-sitter の comment ノード |
| 命名の語彙集計 | フォルダ名・ファイル名・識別子の語の頻度 | 文字列処理。機能推測の材料 |
| 分岐の数（複雑度の**近似**） | `if` / `for` / `while` / `case` / `catch` ノードの計数 | CFG 不要。厳密な循環的複雑度ではない |
| 変更のホットスポット | ファイル別の変更回数・最終更新日・著者数 | `git log`。**名前解決と無関係**に取れる。フル版には無かった軸（下記「副産物」） |
| テスト／生成コード／vendor の判別 | パス規約と生成物マーカーによる分類 | ヒューリスティック。誤分類は起きるので `confidence = medium` 相当 |

#### ②-a 決定的に解けるもの（`confidence = medium`）— 推測を含まない

> **2026-08-26 追記で新設。** 当初は②を一括で `low` にしていたが、**推測を含まないものが混ざっていた**。
> 段階1（スコープ解析）と、閉世界仮定の下で候補が一意に定まる解決は、**推測ではなく演繹**である。

| 出力 | 根拠 | 前提 |
|---|---|---|
| ファイル内の束縛（この識別子はどの宣言を指すか） | 段階1。木 ＋ 言語のスコープ規則で確定 | なし。**完全に確実** |
| リポジトリ内で候補が一意な呼び出し | 閉世界仮定 ＋ 軸B が ○ の言語（C / C#） | 閉世界仮定。破れは候補数で検出可 |
| `static` / ファイルローカルなシンボルの解決 | 同一ファイル内で閉じる | なし。**完全に確実** |
| import / include の解決先（相対パスで書かれているもの） | パス解決 | ファイルが実在すること |

**`high` ではなく `medium` にする理由**: 閉世界仮定に依存する行があるため。仮定が破れる条件（マクロ生成の名前、条件コンパイル、ビルド除外ファイルの同名定義）は列挙できるので、破れを検出した行だけを個別に下げる運用にする。

#### ②-b 名前一致による推測（`confidence = low`）

②-a に該当しない結線。**ここだけが推測。**

| 出力 | 何をするか | 何が解けないか |
|---|---|---|
| 粗いコールグラフ（軸B が × の言語） | `callee_expr` の識別子と関数名の一致で線を引く | オーバーロード、名前空間、同名メソッド（C++ が該当） |
| モジュール間の依存図（パスで書かれていないもの） | path alias / インクルードパス / 名前空間を名前で当てる | `-I` 追加パス、`paths` / `baseUrl`、外部パッケージ |
| 継承・実装関係 | `class Foo : Bar` の `Bar` を名前で当てる | どの `Bar` か（名前空間・同名クラス） |
| 宣言された型 | 型注釈・型名が**ソースに書いてあれば**文字列として拾う | 推論された型（`var` / `auto` / 注釈なし Python / TS の推論） |

**②-b の扱いに関する重要な帰結**（[構想] §2.3・§7.3 との整合）:

§2.3 は「**間違った答えが自信を持って出てくるツールは、答えが出ないツールより有害**」と決めている。名前一致による結線はまさにこのリスクの当事者であり、**L0（抽出層）では線を引かない**。L0 が出すのは事実（`callee_expr` の文字列）だけで、名前一致という**判断**は L2 / L3a 側に置き、利用者が明示的に有効化する「推測モード」として扱う。

**②-a はこの制約の対象外。** 演繹であって判断ではないため、L0 が `callee_id` を埋めてよい。「L0 に判断ロジックを入れない」に反しないのは、**閉世界仮定という明示された前提の下での確定**だから。前提が破れた行は `status = unresolved` と `reason`（`external` / `ambiguous`）で記録され、黙って消えることはない。

これは §7.3 のルール1「L0 に判断ロジックを一切入れない」と一致する。**フル版のために作った層分離が、簡易版でそのまま効く。**

#### ③ 取れない

- 正確なコールグラフ（仮想呼び出し、関数ポインタ、デリゲート、動的ディスパッチ）
- 「この関数の呼び元を漏れなく全部」
- 変数の読み書き箇所の網羅（データフロー）
- 未使用コードの断定
- 推論された型
- マクロ展開後のコード、条件コンパイルの有効枝（tree-sitter は `#ifdef` の内外を**両方**構文木に載せる。[構想] §4.7 の注意）
- 外部ライブラリのシンボル（依存を落とさせないので当然の帰結）
- リフレクション・動的呼び出し（`getattr` / `Type.GetMethod` / `eval`）※**フル版でも解けない**
- 言語をまたぐ呼び出し（FFI）※**フル版でも非スコープ**（D-6）

> 末尾2件は簡易版で失うものではない。**フル版との差分は ①②③ のうち ③ の上7件のみ。**

#### 副産物: Git 履歴という軸

「変更のホットスポット」は名前解決を一切必要としないのに、「どの辺りが詳細解析を要しそうか」（E-1 の用途）に直接効く。**フル版の構想には無い軸**であり、簡易版が単なる下位互換に留まらない可能性がある。E-4 の判断材料になる。

#### 実測: ②-a / ②-b の比率（Phase 0 相当、2026-08-26）

##### 方法

呼び出し式を**形**で分類し（ここは厳密。推測を含まない）、単純識別子の呼び出しだけを閉世界仮定の下で解決した。

| 分類 | 定義 |
|---|---|
| **②-a** | 単純識別子で候補が一意 ／ 同一ファイルの `static` が優先 ／ `self.` `this.` で囲むクラスに存在 |
| **②-b** | 単純識別子だが候補が複数 ／ `self.` だが自クラスに無い（継承先の可能性） |
| **macro** | C の関数形式マクロ呼び出し（`reason = macro_expanded` 相当） |
| **external** | 候補ゼロ（定義がリポジトリ外） |
| **③ 要型解決** | 他オブジェクトのメンバ呼び出し（`a.b()` / `p->b()`） |
| **③ 間接** | 呼び先が式（関数ポインタ等） |

**限界**: 「その形なら解けるはず」を数えたものであり、**正解データとの突合はしていない**。②-a の的中率そのものは別途検証が要る（下記「要実測」）。

##### 読み取れること

**1. 言語で桁が違う。単一の答えにならない。**

**2. C は実測値より実質的に強い。**

`macro` 12〜23% は**呼び先のマクロ定義が特定できている**（展開後は不明だが、どのマクロかは分かる）。`external` の中身は `strcmp` / `strlen` / `printf` / `assert` — **ほぼ libc**。標準ライブラリの関数名辞書を持てば「既知の外部」とラベルできる。

> **C は呼び出しの9割以上について「正体が分かる」。** 本当に不明なのは ③（型解決＋間接）の 5〜7% のみ。

**3. Python の `external` 40.5% は大半が builtins。**

`isinstance`(71) / `getattr`(20) / `int`(16) / `cast`(18)。辞書化すれば「不明」ではなくなる。ただし**②-a に昇格するわけではない**（外部だと分かるだけ）。

**4. `self.` / `this.` の解決は効く。**

commander.js の ②-a 27.3% のうち **24.3% が `this.`** 経由。型推論なしで囲むクラスから解決できる。実装すべき機能として費用対効果が高い。

**5. C# の 5.2% は過小評価。** メンバ呼び出し（706件）の内訳を追加測定した。

| レシーバの形 | 割合 |
|---|---:|
| **型名（static 呼び出し）** | **28.1%** |
| 式（チェーン等） | 26.0% |
| **型が明示 & 型がリポジトリ内** | **19.2%** |
| 型が明示だが型がリポジトリ外 | 16.8% |
| 宣言が同一ファイルに見つからない | 5.5% |
| `var` 宣言（型推論が要る） | 4.2% |

`var` はわずか 4.2%。**型はソースに書いてある**。static 呼び出しと明示型レシーバを実装すれば、C# の ②-a は **5.2% → 概ね 35〜40%** まで上がる見込み。

> **ただし注意**: 到達先の多くは `IRuleBuilder<T>` のような**インタフェース／抽象メソッドの宣言**であり、実装には届かない。これは §7.7 の「切れた線」と同じ形（フル版でも仮想ディスパッチは別途解決が要る）。

### [2026-08-26] E-4. 簡易版とフル版の関係 — **スキーマは共有する。DB は混ぜない**

当初の設問は「独立した別ツールか、フル版の下位互換（同じテーブルに `confidence = low` で入れる）か」だったが、**この二択の立て方が誤りだった**。「スキーマを共有するか」と「同じ DB に混ぜるか」は別の決定である。

#### 決定1: スキーマは共有する

E-1〜E-3 の結果がすべて共有側を指していた。

| 根拠 | 内容 |
|---|---|
| 層分離 | §7.3 の L0〜L3 が簡易版でそのまま成立（②-b を L0 で線を引かない、がルール1 と一致） |
| A-1 / A-2 / A-3 | `status` / `reason` / `confidence` / `lang` / `extractor` / `snapshot` をそのまま使えた |
| B-2 / B-4 | SQLite と `snapshot` は共通 |
| 実測 | C と C# を同じ列に出力でき、列を1つも増やさずに載った |

#### 決定2: DB は混ぜない（同じスキーマ定義・別ファイル）

**混ぜることを既定にしない。** 必要になれば SQLite の `ATTACH` で後から結合できるため、既定で混ぜる理由が無い。

混ぜると起きること（混ぜない判断の根拠）:

1. **同じ呼び出しが2行になる** — 簡易版が `unresolved / needs_type`、フル版が `resolved` と言った同じ箇所が併存する。§7.3 のフィルタ原則 `WHERE status='resolved'` 自体は書けるが、**件数を数えると二重計上**する
2. **どちらを正とするかのルールが要る** — これは L2 / L3a の話であり、L1 に持ち込むと層分離が濁る

**ただし主キーは混在に耐える形にする**（[構想] §3.1.5）。運用として混ぜないことと、混ざったときに壊れないことは別物で、後者を捨てる理由が無いため。

#### 決定3: `confidence` ではフル版と簡易版を区別しない

A-2 は「簡易版の結果は `low`」を前提にしていたが、**E-3 で ②-a を `medium` に格上げした時点でこの前提は崩れている**。閉世界仮定の下で候補が一意に定まる解決は推測ではなく演繹だから。

**区別は `extractor` 列で行う**（A-3 がこの列を全テーブルに持たせているのがここでも効く）。

#### 決定4: フル版への追随改訂（凍結は維持）

**改訂は「簡易版に合わせる」ためではない。** 簡易版の検討で**フル版自身の欠陥が実測により判明した**ため。放置するとフル版の再開時に同じことを再発見することになる。

| 5 | **主キーを明記** | `id` 単独では抽出器を変えて再抽出したときに衝突する | [構想] §3.1.5 |

### [2026-08-26] E-1. 想定用途と最小の出力 — **4テーブル・5レポート。段階1の最小版は必須要件**

初期対象言語は **C と C#**。C が最も価値が出るという E-3 の実測を受けつつ、**C だけではデータセットが C に寄る**ため、最も遠い言語と組ませて汎用性を担保する。実際、この選択により **C だけでは気づけない欠陥が2件露呈した**（本ファイル E-1 の発見1・発見2）。

#### 最小の出力

**4テーブル**（L1、SQLite）: `files` / `symbols` / `refs` / `comments`

**5レポート**（L3a）: 概観 ／ **機能の見取り図** ／ ホットスポット ／ コンポーネント依存 ／ **解決サマリ**

- **`comments` を最小に含める**。doc コメントは「この関数が何をするか」を人が書いた唯一の記述で、名前解決を一切必要としない。実測で C# の定義の **49.8%**（平均239文字）、cJSON の **34.2%** に付いていた。**簡易版がフル版と同等以上になりうる唯一の領域**でもある（コンパイラのフロントエンドはコメントを捨てる）
- **「解決サマリ」を最小に含める**。§2.3 の「不確かさを黙って隠さない」を**出力の一部**にするため

#### 言語固有概念を列に持ち込まない

`kind` / `container_id` / `visibility` / `refs.kind` / `refs.reason` の汎用語彙へ写す。**言語に無い概念は「行が出ない」だけで、列は共通のまま。** C と C# を同じ列の SQLite へ実際に出力して確認済み（列を1つも増やさずに載った）。

#### 段階1（スコープ解析）の最小版は**必須要件**

改良A（同一 container 優先）／B（レシーバの宣言型を使う）／C（型名なら static 呼び出し）／D（ローカル束縛は `via_function_pointer`）。

**「あると精度が上がる」機能ではなく「無いと嘘をつく」機能である。** C の実測では `resolved` 率が 0.0 ポイントしか動かないのに、**関数ポインタ経由の呼び出しを「リポジトリ外の関数」と誤報告していた 17〜18 件が消えた**。C# では `resolved` が **5.5% → 31.8%**。

4つとも「1ファイルの構文木 ＋ リポジトリ内の定義表」で完結し、**軸2 = ゼロを崩さない**。

#### 初版の天井（明示する境界）

チェーン呼び出し（`a.b().c()`）と `var` の型推論は**入れない**。本物の型推論＝段階5の領域。C# に残る `needs_type` 40% がこれ。

#### フル版との関係

**部分集合 ＋ α。** 出すものはフル版の部分集合だが、**git メトリクスはフル版に無い軸**なので厳密な包含関係ではない。→ E-4 で扱う。

### [2026-08-26] E-2. インストール水準 — **2軸に分解。軸1 =「軽い」／軸2 = ゼロ**

当初の E-2 は「利用者のマシンに何を入れさせるか」という**1軸しか持っていなかった**。実際にはもう1軸ある。

| 軸 | 問い | 対象 |
|---|---|---|
| **軸1** | 利用者の**マシン**に何を入れさせるか | ツール側 |
| **軸2** | 利用者に**解析対象**について何を用意させるか | 対象リポジトリ側 |

#### 軸1 = 「軽い」（Python 3.10+ ＋ `pip install` 1コマンド）

**採用理由**: Python と pip が使えない前提を置くと、解析するための言語処理系から用意する話になり本末転倒。開発者のマシンに Python が無いケースは想定しない。

「完全ゼロ」（単一実行ファイル）を採らない理由: Go / Rust での実装を意味し、**B-2**（ストアは SQLite ＝ Python 本体同梱だから追加依存ゼロ）と **B-3**（ローダーは Python）の根拠がまるごと無効になる。tree-sitter 本体は C なので Go / Rust からも使えるが、実装言語の選び直しは既存の決定を再利用できなくする。配布の手間に対して失うものが大きい。

**受け入れる制約**: オフラインの閉じた環境では wheel の持ち込みが必要。これは既知の穴として受け入れる。

#### 軸2 = ゼロ（ビルドコンテキストを要求しない）

要求するのは「**ソースツリーが読める状態にあること**」だけ。[構想] §7.7 が抽出器の起動条件として挙げていたもの（`compile_commands.json` / `.sln`・`.csproj` / `tsconfig.json` ＋ `node_modules` / 依存パッケージの入った実行環境）を**一つも課さない**。

**採用理由**: 想定用途は「初見のソースコードの一次解析」であり、**その状況でビルドが通る状態にあることの方が稀**。ビルドが通らないリポジトリ、依存を落とせない環境、zip を展開しただけのツリー、受け取った一部だけのソース — これらが全部そのまま対象になる。

> **補正（2026-08-26）**: 軸2 = ゼロは**二択ではなく既定値**である。追加のソースツリーを外部から渡せる設計にすれば、閉世界の**境界はパラメータになる**（E-3 の「閉世界の境界はつまみ」）。要求を課さないのは既定動作の話であって、広げる手段を持たないという意味ではない。

#### この2軸のうち、実現手段を確定させるのは軸2

名前解決を行うツール（libclang / Roslyn / TypeScript Compiler API）は**ビルドコンテキスト無しでは機能しない**（プロセスは動くが型が解決できない）。したがって軸2 = ゼロは、**[構想] §4.1 の選定基準1（意味解析を持っているか）を放棄する**ことと同義であり、使える手段は構文解析までに絞られる。

→ **tree-sitter が主力になる。** [構想] §4.7 はこれを「まだ抽出器を書いていない言語の暫定対応」と格下げしているが、**簡易版ではこの位置づけを覆す**。

#### 効果の非対称性（軸1から詰めてはいけない理由）

軸1を「完全ゼロ」にしても、軸2を課せば「まず cmake を通してください」が残るので利用者の負担は消えない。逆に軸1が「軽い」でも軸2がゼロなら、体験は **clone → 1コマンド → 結果が出る** になる。**効果の大半は軸2にある。**

軸1から議論すると実装言語の選定に入ってしまい、用途の話に戻れなくなる。順序として軸2を先に確定させた。

**記載先**: 本ファイル E-3（この決定を前提とした線引き）。E-1 / E-4 の決定後、簡易版の構想文書へ移す

### [2026-08-25] A-1. `resolution` の値セット — **`status` と `reason` の2列に分離**

1列に「解決できたか」と「なぜできなかったか」という粒度の異なる2軸が同居していたのが原因。分離して両方を残す。

| 列 | 問い | 値 |
|---|---|---|
| `status` | どの状態か | `resolved` / `unresolved` / `not_applicable` / `not_extracted` |
| `reason` | なぜ解決できなかったか（`status = unresolved` のときのみ） | `via_function_pointer` / `virtual_unresolved` / `macro_expanded` / `unknown` |

**採用理由**: §7.3 のフィルタ原則が `WHERE status = 'resolved'` と素直に書ける。`reason` に値を追加しても `status` の値域が汚れず既存クエリが壊れない。「未対応の言語だから空」と「その言語に概念が無いから空」が区別できる。

**記載先**: [構想] §3.1 / §3.1.1 / §3.3、[理想] §3.3 ④（採用済みと追記）、[現実] §「初版スキーマ」

> **改訂（2026-08-26、E-4 で確定）**: `reason` に **`external`**（定義が解析対象の外）／**`ambiguous`**（対象内の候補が複数）／**`needs_type`**（メンバ呼び出しでレシーバの型が不明）の3値を**追加した**。本決定が採用理由に挙げた「`reason` に値を追加しても `status` の値域が汚れない」性質の、想定どおりの使い方。[構想] §3.1.1 に反映済み。

### [2026-08-25] A-2. `confidence` 列 — **`high` / `medium` / `low` の enum で追加**

§7.4-2 が必須としていた信頼度列を全テーブルに追加。数値（0.0〜1.0）は採らない。

**採用理由**: libclang も Jedi も確率値を返さないため、数値にすると根拠のない小数を書くことになり、§2.3 の「間違った答えが自信を持って出てくるツールは有害」に逆行する。enum なら抽出器が根拠を持って言える粒度に一致する。

`status`（解決できたか＝事実）/ `reason`（できなかった理由＝事実）/ `confidence`（どれだけ信じてよいか＝判断）は役割が重複しない。Python の解決結果は `status = resolved` かつ `confidence = low` になる。

> **訂正（2026-08-26、E-4）**: 当初「簡易版（構文解析のみ）の結果は一律 `low`」と考えていたが誤り。閉世界仮定の下で候補が一意に定まる解決は**推測ではなく演繹**で `medium` に相当する（E-3 の ②-a）。**`confidence` でフル版と簡易版を区別することはできず、区別は `extractor` 列で行う。**

**記載先**: [構想] §3.1 / §3.1.2

### [2026-08-25] A-3. `lang` / `extractor` / `snapshot` の適用範囲 — **全テーブルに持たせる**

`symbols` から JOIN で引く案は、未解決の行（`callee_id` が空）で対応先が無く、抽出器のバージョンだけを上げて再抽出したケースでも破綻するため却下。

L0 の中間ファイルではメタ情報行に1回だけ書き、L1 取り込み時に各行へ展開する。**冗長になるのは L1 のみ**で、手書きする中間ファイル側は冗長にならない。

**記載先**: [構想] §3.1 / §3.1.3 / §7.6

### [2026-08-25] B-1. SCIP シンボルIDのマッピング規則 — **`local` スキームを定義**

SCIP の `<scheme> <package-manager> <package-name> <version> <descriptor...>` のうち、C/C++ にはパッケージ座標に相当する概念が無いことが問題だった。

自リポジトリのコードは `local <repo-name> <snapshot> <descriptor...>`、外部ライブラリは `scip-python` / `scip-typescript` が出す本来の座標（`pypi requests 2.31.0` 等）をそのまま受け入れる。両者は同じ名前空間に共存する。

**要実測（Phase 0）**: descriptor を各言語のネイティブIDから機械的に生成できるか。特に C++ のオーバーロード・テンプレート。

> **⚠ 改訂済み（2026-08-26、E-4 で確定）**: **C# で 17.7% のシンボルが ID 衝突で消えた**（オーバーロード）。C は 2.3%。descriptor に**パラメータの型名リスト**を含めることを必須とした。型注釈が無い言語はアリティでフォールバック。出現順の連番は編集で変わるため採らない。C++ を待たずに C# で顕在化した。詳細は E-1「発見1」、[構想] §3.2.2。
