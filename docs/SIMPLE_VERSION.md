# 簡易版 構想

**作成日**: 2026-08-31
**ステータス**: **確定**（C-2 / E-5 を本文書で決定した）
**位置づけ**: **簡易版の全体像を1本にまとめた文書。** ここを読めば「何を作るのか」が分かる。

## 0. この文書について

### 何を書くか

**簡易版（インストール負担を最小にした版）の全体像。** 用途・前提・何が取れるか・何を出すか・どう作るか。

### 何を書かないか — **再掲を作らない**

| 知りたいこと | 見る場所 |
|---|---|
| **列の定義・値域・主キー** | **`SCHEMA.md`（正本）。本文書には書かない** |
| ある列がどう決まってきたか | `SCHEMA_INDEX.md` |
| **なぜそう決めたのか**（実測・却下案・経緯） | **`DECISIONS.md`（正本）** |
| まだ決まっていないこと | `OPEN_DECISIONS.md` |
| 層分離の規則、L0 形式、増分ロード、テスト対象 | `CODE_ANALYSIS_CONCEPT.md`（以下 **[構想]**）の §2.3 / §7.3 / §7.6 / §8 |
| 言語別に「その概念が存在するか」 | `ANALYSIS_VIEWPOINTS.md` |
| フル版（ツール選定・ライセンス・インストール要件） | `full-version/` |

> **これは方針ではなく、失敗から来た制約である。** 列定義の写しが5箇所にあった結果、
> 追随漏れが構造的に起きた（F-8。`§7.6` は「現状の3テーブル」のまま取り残されていた）。
> **本文書に列を書けば3つ目の写しができる**ので、書かない（F-1 決定）。

### フル版との関係

**捨てていない。** [構想] は「厳密版」として有効で、簡易版はその下位互換ではない。

| | フル版 | 簡易版 |
|---|---|---|
| 主力ツール | libclang / Roslyn / TS Compiler API | **tree-sitter** |
| 利用者への要求 | Python / .NET SDK / Node / clang / cmake ＋ **ビルドが通る状態** | **Python 3.10+ と `pip install` 1コマンドだけ** |
| 名前解決 | 意味解析による厳密な解決 | **閉世界仮定つきの演繹**（②-a）まで |
| スキーマ | **共有する**（`SCHEMA.md`） | 同左 |
| DB | **混ぜない**（同じ定義・別ファイル）。必要なら `ATTACH` | 同左 |
| 区別 | `extractor` 列で行う（`confidence` ではない） | 同左 |

**簡易版が勝る領域もある。** doc コメントと Git 履歴（→ §3.4）。

## 1. 何を作るのか

**ソースコードから構造化データ（ファクト）を抽出し、その上で可視化・分析を行う仕組み。**

### 想定用途: 初見のソースコードの一次解析の補助

嬉しいのは**全体像の把握**であり、網羅的な正確さではない。

| 知りたいこと | 名前解決が要るか |
|---|---|
| どのフォルダに何の機能があるか | 不要 |
| どの辺りが詳細解析を要しそうか | 不要 |
| 規模感・構造の偏り | 不要 |
| モジュール間の大まかな依存 | ほぼ不要 |
| 「この関数の呼び元を漏れなく全部」 | **必要**（ここだけフル版の領分） |

**この用途はフル版の能力のごく一部しか使っていない。** だから名前解決を捨てても大半は満たせる——
これが簡易版の出発点である（E-2）。

### 貫く原則

**[構想] §2.3 —「間違った答えが自信を持って出るツールは有害」。**

本文書の設計判断は、ほぼすべてこの原則に帰着する。**解決率を上げることより、
名乗りを実態に合わせることを優先する**（§3.3 / §4.3 / §5.4 に具体例）。

## 2. 前提 — 2つの軸（E-2、確定 2026-08-26）

当初は「利用者のマシンに何を入れさせるか」の1軸しか見ていなかった。**2軸に分けたのが転換点。**

| 軸 | 問い | 結論 |
|---|---|---|
| **軸1** | 利用者の**マシン**に何を入れさせるか | **Python 3.10+ ＋ `pip install` 1コマンド** |
| **軸2** | 利用者に**解析対象**について何を用意させるか | **ゼロ**（ソースツリーが読めればよい） |

**効果の大半は軸2にある。** 軸1 を完全ゼロ（単一実行ファイル）にしても、軸2 を課せば
「まず cmake を通してください」が残る。

### 軸1 の実測（F-15、2026-08-31）

| パッケージ | 版 | `Requires-Python` | 実行時依存 |
|---|---|---|---|
| `tree-sitter` | 0.26.0 | **`>=3.10`** | なし |
| `tree-sitter-language-pack` | 1.15.8 | **`>=3.10`** | `tree-sitter>=0.23` |

**Python 3.10+ は tree-sitter 自身の要求**であり、下げようがない（暫定値ではない）。
`sqlite3` は Python 本体に同梱、C コンパイラ不要、計約 7.6MB、371言語対応、MIT。

**受け入れる穴**: オフラインの閉じた環境では wheel の持ち込みが要る。

### 軸2 はゼロだが、境界はパラメータ

**ゼロは二択ではなく既定値。** 追加のソースツリーを渡せる設計にすれば、閉世界の境界はつまみになる。

| レベル | 渡すもの | 到達できるもの | 評価 |
|---|---|---|---|
| **0** | 何も渡さない | 解析対象ツリーの中だけ | **既定** |
| **1** | 追加ソースツリー | **定義**まで | **費用対効果が最大** |
| 2 | システムヘッダ | 宣言まで | **実測で割に合わないと判明**（下記） |
| 3 | ビルドコンテキスト | フル版 | 簡易版では採らない |

> **レベル2 を落とした実測**: `/usr/include/stdio.h` で試したところ、`extern` 宣言 138 行に対し
> tree-sitter が取れた関数宣言は **16 件のみ**（ERROR ノード 136）。`__THROW` / `__nonnull` 等の
> 属性マクロで宣言ごと ERROR に落ちる。**システムヘッダは tree-sitter が最も苦手な入力。**
> 代案として「標準ライブラリの関数名辞書」を持つ方が確実で安い（→ §4.2）。

**どの境界で走ったかは `analysis_run` に記録する**（F-4）。記録が無いと `external` という同じ語が
実行ごとに別のことを指す。

## 3. 何が取れて、何が取れないか

### 3.1 4段階の線引き（E-3、確定 2026-08-26）

| 分類 | 中身 |
|---|---|
| **① 取れる** | ディレクトリ構造、規模の偏り、関数・クラス一覧と位置、import/include/using の記述、呼び出し**式**、コメント密度と TODO 分布、命名の語彙、分岐数、**Git 変更ホットスポット**、テスト/生成コード/vendor 判別 |
| **②-a 決定的に解ける** | ファイル内の束縛、`static` 等ファイルローカルなシンボル、**リポジトリ内で候補が一意な呼び出し**、相対パスの import/include |
| **②-b 名前一致の推測** | 粗いコールグラフ、パスで書かれていない依存、継承関係、ソースに書かれた型 |
| **③ 取れない** | 正確なコールグラフ、呼び元の網羅、データフロー、未使用コードの断定、推論された型、マクロ展開後のコード、外部ライブラリのシンボル |

**②-a を ②-b から分けたのが設計の要。** 解けるかを決めるのは「段階」ではなく次の2軸である。

| 軸 | 問い |
|---|---|
| **軸A: 情報の所在** | 自ファイル内 / リポジトリ内の他ファイル / **リポジトリ外** |
| **軸B: 名前の一意性** | 名前だけから一意に定まるか（オーバーロード・仮想・動的で崩れる） |

**閉世界仮定**（解析対象ツリーがプログラムの全体）を明示的に置けば、リポジトリ内で候補が一意な
呼び出しは**推測ではなく演繹**になる。しかも**仮定の破れは候補数で検出できる**
（0個 = `external`、複数 = `ambiguous`）。

> **②-b は L0 で線を引かない。** 名前一致という判断は L2 / L3a の「推測モード」に置く。
> [構想] §7.3 **ルール1**（L0 に判断ロジックを入れない）と一致する——
> **フル版のために作った層分離が、簡易版でそのまま効いた。**

### 3.2 実測 — 言語で桁が違う（E-1、ビルドは一切していない）

| プロジェクト | 言語 | 呼び出し | **②-a** | ②-b | macro | external | ③型解決 | ③間接 |
|---|---|---:|---:|---:|---:|---:|---:|---:|
| cJSON | C | 526 | **66.5%** | 0.0% | 12.4% | 16.2% | 4.9% | 0.0% |
| cmark | C | 1,381 | **59.9%** | 0.0% | 23.2% | 11.4% | 3.5% | 2.0% |
| tinyxml2 | C++ | 909 | **22.2%** | 19.9% | 15.4% | 6.3% | 29.5% | 6.7% |
| requests | Python | 986 | **17.2%** | 2.9% | 0.0% | 40.5% | 39.2% | 0.1% |
| commander.js | JS | 758 | **27.3%** | 0.0% | 0.0% | 7.4% | 64.9% | 0.4% |
| FluentValidation | C# | 1,022 | **5.4%** | 12.3% | 0.0% | 12.8% | 69.1% | 0.6% |

**単一の答えは無い。出力の主役を言語で変える。**

- **C は実質9割が「正体判明」**。②-a 6割 ＋ macro（呼び先のマクロ定義は特定済み）＋ external の中身はほぼ libc。本当に不明なのは ③ の 5〜7% だけ
- **Python の external 40.5% は大半が builtins**。辞書化で「不明」ではなくなるが ②-a には昇格しない
- **`this.` / `self.` の解決は効く**。commander.js の ②-a 27.3% のうち 24.3% が `this.` 経由
- パースは健全（Python / JS / C# は **ERROR ノード 0**）

### 3.3 ★ 的中率 — 「形の上で解ける」と「実際に解けている」は違う（F-16、2026-08-31）

**②-a は `status = resolved` / `confidence = medium` を名乗るのに、
正しい先を指しているかを一度も検証していなかった。** 上の比率はすべてこの前提の上に載っていた。

**C と C# の両方を標本で検証した**（規則ごとに層化抽出し、ソースを突き合わせて人手判定）。

| 言語 | 規則 | 母集団 | 標本 | 正 | **的中率** |
|---|---|---:|---:|---:|---:|
| **C** | 同一ファイルの `static` 優先 | 199 | 25 | 25 | **100%** |
| **C** | 閉世界で候補が一意 | 151 | 25 | 25 | **100%** |
| C# | 閉世界で候補が一意 | 4 | 4（全数） | 4 | 100% |
| C# | 型名 → static | 79 | 20 | 19 | 95% |
| C# | 同一 container（`this.` 省略） | 139 | 20 | 16 | 80% |
| **C#** | **レシーバの宣言型** | 101 | 20 | 5 | **25%** |
| **C#** | **`this.` / `base.` 経由** | 2 | 2（全数） | 0 | **0%** |

- **C: 50/50（100%）。** 95% 信頼下限で 94.2% 以上
- **C#: 44/66（66.7%）。** `resolved` 31.8% のうち**実際に正しいのは約 21.1%——名乗りが実態の 1.5 倍**

誤り 22 件の原因は 2 つだけ。**オーバーロードの取り違え 20 件**（名前一致で先頭を機械的に選んでいた。
`SetValidator` は 4 オーバーロード）と、**`base.` を自分自身に向けた 2 件**
（`base.` なのに自分の型から探し始めるので構造上かならず外し、**偽の自己再帰エッジ**まで作る）。

> **この検証で列が1つ増えた。** 的中率が規則ごとに 25%〜100% とばらけたため、
> **②-a を一律 `medium` とする割り当てが成立しない**。規則ごとに `confidence` を決めるには
> 「どの規則で解いたか」がデータに要る → **`refs.resolved_by`**（定義は `SCHEMA.md`）。
> `symbols.visibility_source` とまったく同じ構造である。

**C# はオーバーロードのある呼び出しを `resolved` にしない**（`unresolved` / `ambiguous` に落とす）。
これで `resolved` は 325 → 204 件 = **20.0%** になり、実測の的中率 **21.1%** とほぼ一致する。
**数字を下げる措置ではなく、名乗りを実態に合わせる措置。** §2.3 の直接の適用である。

### 3.4 簡易版がフル版と同等以上になる領域

| 領域 | なぜ勝てるか | 実測 |
|---|---|---|
| **doc コメント** | コンパイラのフロントエンドはコメントを捨てる（libclang は特別な指定が要り、Roslyn では trivia）。**tree-sitter は comment を第一級ノードとして持つ** | doc を持つ定義: cJSON 34.2% / cmark 22.6% / **FluentValidation 49.8%**。ファイル先頭コメントは FluentValidation で **130/137 ファイル** |
| **Git 履歴** | 名前解決を一切必要としない。**フル版の構想には無い軸** | 「どの辺りが詳細解析を要しそうか」に直接効く |
| **`#ifdef` の両枝** | フル版は1構成しかパースしないので、Linux 上では `#ifdef _WIN32` の中身が見えない | — |

**doc コメントは「この関数が何をするか」を人が書いた唯一の記述**で、名前解決を必要としない。
命名の語彙集計より遥かに直接的に「どのフォルダに何の機能があるか」に答える。

> **`comments` は「コメント構文」ではなく「人が書いた説明」の器**として定義してある。
> Python の docstring は文字列リテラルなので `comment` ノードに入らない（requests は定義の 65% が docstring）。

### 3.5 壊れた入力への態度

tree-sitter は壊れたコードからも木を返すが、**黙って痩せた結果を返す**。

| 入力 | 回復 |
|---|---|
| 式の破損、未知のマクロ修飾 | **完全に回復**（実測 3/3） |
| **括弧の不均衡** | **後続を巻き込んで全滅**（実測 **0/3**。関数を1つも拾えない） |

**ERROR ノード数を数えて記録することを L0 の必須要件とする。** 数えなければ
「静かな取りこぼし」がそのまま残り、§2.3 の当事者になる。
欠落は `files`、誤りは `confidence` の2段構えで表す（F-6。列は `SCHEMA.md`）。

## 4. 何を出すのか

### 4.1 ファクト（L1）

**4テーブル ＋ 実行メタ1テーブル。列の定義は `SCHEMA.md` を見ること（本文書には書かない）。**

| テーブル | 持つもの |
|---|---|
| `files` | ファイル単位の事実（規模、コメント行数、パースの健全性、git メトリクス） |
| `symbols` | 定義されたもの（関数・型・マクロ・名前空間…） |
| `refs` | 参照関係（呼び出し・import・変数参照） |
| `comments` | **人が書いた説明**（doc / ファイル先頭 / マーカー） |
| `analysis_run` | **どの境界で走ったか**（レベル・追加ツリー・辞書・ツール版） |

### 4.2 初版の必須要件 — 「あると精度が上がる」ではなく「無いと嘘をつく」もの

| # | 要件 | 無いとどうなるか |
|---|---|---|
| 1 | **段階1（スコープ解析）の最小版** | 関数ポインタ経由の呼び出しを「リポジトリ外の関数」と**誤報告する** |
| 2 | シンボルIDにシグネチャを含める | C# で **17.7%** のシンボルが ID 衝突で**静かに消える** |
| 3 | C# の file-scoped namespace 対応 | 名前空間が ID から欠落する |
| 4 | 標準ライブラリ辞書 | `external` が「未知」と「既知の libc」に分けられない |
| 5 | C の `#include` 相対解決 | リポジトリ内の依存が引けない |
| 6 | ERROR ノードの記録（§3.5） | 取りこぼしが静かに起きる |
| 7 | **`base.` は基底から探す**（F-16 決定3） | 必ず自分自身を指し、**偽の自己再帰エッジ**を作る |

> **要件1 の根拠が重要。** 4改良（同一 container 優先／レシーバの宣言型／型名なら static／
> ローカル束縛は `via_function_pointer`）の before/after を測ったところ、
> **C は `resolved` 率が 0.0 ポイントしか動かないのに、誤分類が 17〜18 件消えた。**
> 解決率ではなく §2.3 が採用理由である。C# では `resolved` が 5.4% → 31.8% になった
> （**ただし 31.8% は最終値ではない**。F-16 決定2 でオーバーロードを降格すると **20.0%** になる → §3.3）。

**標準ライブラリ辞書は `resolved` に格上げしない。** `dst_id` に座標を入れ、`status` は
`unresolved` のまま（F-4 決定2）。格上げすると C の解決率が 66.5% → 8割超に跳ね上がるが、
**コードについて分かったことは1つも増えていない**——名前が libc のリストに載っていた、というだけ。

### 4.3 レポート（L3a）

**5レポート。ただしこれは初版の最小セットであって、出せるものの上限ではない**（[構想] §7.3 ルール4）。

| # | レポート | 中身 |
|---|---|---|
| 1 | **概観** | ディレクトリ別のファイル数・行数・言語構成 |
| 2 | **機能の見取り図** | ディレクトリ／名前空間ごとに**ファイル先頭コメント＋主要シンボルの doc を集約**。「どのフォルダに何の機能があるか」への直接の答え |
| 3 | **ホットスポット** | 規模 × 変更頻度（git）× 分岐数 × **doc の欠落率**。「どこから読むか」の答え |
| 4 | **コンポーネント依存** | ディレクトリ／名前空間の単位に呼び出しを集約した図 |
| 5 | **解決サマリ** | `status` / `reason` / `confidence` / `resolved_by` の分布 |

> **5 を最小に含めるのが最重要。** 「呼び出しの 66% が確定、12% がマクロ、16% が外部」を先に出すことで、
> §2.3 の「不確かさを黙って隠さない」が**出力の一部**になる。
> `analysis_run` の内容（どの境界で走ったか）も併記する（F-4 決定3）。

**レポート4 は C# でも成立する**（F-10）。E-1 は「C# では描けない」と結論していたが、
それは改良A〜D の**前**（`resolved` 5.4%）の測定だった。

**初版の構成（F-16 決定2 でオーバーロードを降格した後）で測った値**が下表の右端である。

| | 改良前（E-1） | 改良後（F-10 測定時） | **初版の構成** |
|---|---|---|---|
| `resolved` | 55（5.4%） | 325（31.8%） | **204（20.0%）** |
| エッジを持つコンポーネント | 6 中 **3** | 6 中 6 | **6 中 5** |
| コンポーネント間エッジ | 4 本（ほぼ自己ループ） | 6 種 / 97 件 | **6 種 / 94 件** |

**降格しても図の形はほぼ変わらない**（コンポーネント間エッジは 6 種のまま、呼び出しも 97 → 94 件）。
降格されたのは**自己ループ側に偏っていた**（228 → 110 件）ためである。

> **ただし乗ったのは全呼び出しの 9.2% にすぎない。**
> 最大の 1 本（63 件）を除くと**残り 31 件**しかない。
> E-1 の反証「**集約はノイズを減らすが、欠落は埋めない**」は今も有効である。
> **94 本で描いた図を、網羅した図として見せてはならない。**
> → レポート4 には**集約前の `status` 分布を必ず添える**（F-10 決定2）。

> **この表は齟齬の検出から生まれた。** F-10 の測定は F-16 より前で、
> **オーバーロードの取り違え 121 件を `resolved` に数えたまま**だった。

## 5. どう作るのか

### 5.1 層（[構想] §7.3 が正本）

```
L0  抽出層 (extractors/)   事実のみを出す。判断しない。捨てない。
                           ↓ 追記のみ
L1  ファクト層 (facts/)    スキーマ固定。信頼度つき。不変。   ← 唯一の境界
                           ↓ 派生（再生成可能）
L2  派生層 (derived/)      到達可能性、推移閉包など
                  ┌────────┴────────┐
L3a 理解層 (views/)        L3b 検出層 (rules/)
    図、レポート、検索          ルール評価 → findings
```

守る規則は4つ（全文は [構想] §7.3）。**ルール4 が簡易版の設計の背骨**になる。

> **ルール4: 解析側とアプリ側を L1 で切り、アプリは後から足せる形にする**（2026-08-31）
>
> | | 変わる理由 |
> |---|---|
> | **解析側**（L0 / L1 の生成） | 言語が増える。規則の精度が上がる |
> | **アプリ側**（L2 / L3a / L3b） | **実際のデータを見て「何を読みたいか」を思いつく** |
>
> **理由**: 取得したデータから何を読み出すかは、実際のデータを見て初めて思いつく。
> 最初から決め打ちにすると、**出来合いのツールを使わず自前でファクトを持つ意味が失われる**——
> 自前で持つのは、後から自由に問いを立てられるようにするためである。

**この文書自身がその実例を4件出している。**

| 出来事 | 先に設計を決めていたら出てこなかった問い |
|---|---|
| E-3 の副産物 | Git 履歴が「どこから読むか」に効くと**測ってから**気づいた |
| E-1 の発見3 | `external` 上位が `predicate` / `func` / `action` だったのを見て、段階1 が必須と分かった |
| F-10 | レポート4 が C# で描けるかは、改良後のデータで測り直して結論が変わった |
| F-16 | ②-a の的中率を測ったら**列が1つ足りない**ことが分かった |

### 5.2 実装構成（B-3）

GUI は初版で作らないが、後から安く足せるように3点を初版から守る。

1. **ロジックは `core/`、CLI は薄いラッパー**
2. **ジョブ設定ファイル（TOML）**
3. **構造化された進捗出力**

抽出器は独立プロセス（API 呼び出しではない）。L1 は SQLite（`facts/db.sqlite`）で追加依存ゼロ。

**B-3 が「実行の入口」を後付け可能にし、ルール4 が「出力の出口」を後付け可能にする。**
両者は §5.3 の決定で合流する。

### 5.3 ★ L3a の設計 — C-2 の決定（確定 2026-08-31）

> **前提の整理**: 出どころはロードマップの「**Mermaid または自作 HTML** でコールグラフを出力」という併記だった。
> **この二択そのものが誤った設問である。** ルール4 でプラグイン形式にする以上、
> 両方を別プラグインとして持てるので、選ぶ必要が無い。
> **決めるべきは描画ライブラリではなく、プラグインの受け口の側。**

#### 決定1: 受け口は「1レポート1ファイル・宣言ベース登録」

| 項目 | 決定 | 理由 |
|---|---|---|
| **単位** | `views/<id>.py` の**1ファイル1レポート** | 追加・削除・差し替えが本体にも L1 にも触れずに済む（ルール4） |
| **登録** | モジュールが `REPORT` を公開していれば採用（ディレクトリ走査） | **命名規約にしない。** ファイル名を変えると壊れるが、中身で判定すれば壊れない |
| **入力** | **読み取り専用の `sqlite3.Connection`** ＋ `ctx`（`analysis_run` の内容、`scope` 等） | **ORM を挟まない。** L1 が SQLite であることは B-2 の決定であり、**SQL がそのまま資産になる**。ORM を挟むと `SCHEMA.md` の写しがコード側にでき、F-1 で潰した問題が再発する |
| **出力** | `Artifact` のリスト（名前・メディア型・内容）を**返す**。ファイルに書くのは本体 | プラグインがファイルシステムに触ると出力先の規約が散る。**同じレポートを別の出口（GUI）へ流せる**（§9 のローカル Web UI） |
| **前提条件** | `requires` に必要な列・条件を宣言。満たさなければ**描かずに理由を出す** | §2.3。黙って劣化させない |

> **`requires` が要る具体例**: `git_state = 'none'`（zip を展開しただけのツリー）では
> ホットスポットの4軸のうち「変更頻度」が消える。**黙って3軸で描くと、それと分からない。**

#### 決定2: 描画手段は Mermaid と単一 HTML の**両方**。排他にしない

| 手段 | 位置づけ | 理由 |
|---|---|---|
| **Mermaid**（テキスト） | **既定** | 依存ゼロ。テキストなので **diff が取れる**。GitHub やエディタでそのまま見える |
| **単一 HTML** | 併存 | 大きいグラフで Mermaid が破綻する。対話が要る。**§9 のローカル Web UI と地続き** |

**外部バイナリを要求する手段（Graphviz など）は採らない。** 軸1 に違反する。
HTML 側の JS は同梱（vendoring）し、`pip install` だけで完結させる。

#### 決定3: 規模は既定で絞る。**絞ったことを必ず図に書く**

**実測**: ②-a の本数は cJSON **350 本** / cmark **827 本**。Mermaid は数百ノードで実用外になる。
一方 F-10 の C# コンポーネント図は **6 本**——**効くのは C のコールグラフ側**である。

| 規則 | 内容 |
|---|---|
| 既定の粒度 | **コンポーネント（ディレクトリ／名前空間）**。関数粒度は `scope` 指定時のみ |
| 上限超過時 | 描かずに「上位 N のみ」へ落とす |
| **必ず併記** | **省略した件数と基準**。および集約前の `status` 分布（F-10 決定2） |

**F-10 決定2 と同じ考え方。** 間引いた図を網羅した図として見せないための規約であり、§2.3 の適用。

## 6. 実装計画

### 6.1 ★ 着手順 — E-5 の決定（確定 2026-08-31）

**C から始める。C で5レポートを通してから、列を増やさずに C# を載せる。**

> **[構想] §10.1 はフル版の Phase 1 を C# にした**が、理由は「C/C++ は前提条件（cmake / clang）の
> 準備が重いから」だった。**軸2 = ゼロにより準備の重さは消えている**ので、この理由は成立しない。

| 根拠 | 内容 |
|---|---|
| **F-16** | **C は的中率 100%（50/50）で検証済みで手直しが無い。** C# は 66.7% で、**決定2・決定3 の修正が先に要る** |
| **E-1** | C は ②-a 6割で、**コールグラフを主役にできる唯一の言語**。レポート側の設計は主役が成立する言語で固めた方が早い |
| **言語特性** | C にはオーバーロードも仮想ディスパッチも無い。**F-16 の誤り 22 件はすべて C# 固有の機構**に由来する |

**C 専用にはしない。** E-1 が初期対象を C + C# にした理由（C だけだとデータセットが C に寄る）は生きている。
**列を1つも増やさずに C と C# が同じテーブルに載ることは実測済み**（`tools/emit-generic-schema.py`）。

> **未測定の材料について**: E-3 は「段階1の実装コスト」を**着手順を決める材料**として挙げているが、未測定である。
> ただし **C 側の段階1 は改良D（ローカル束縛の検出）だけで誤分類 17〜18 件が消えている**ため、
> **C 先行の判断は実装コストの測定を待たずに下せる。** 測定が効くのは「C# にどれだけかけるか」の側。

### 6.2 順序

| 段 | 内容 | 完了の判定 |
|---|---|---|
| **1** | L0（C）＋ L1 ローダ | `SCHEMA.md` の DDL に cJSON / cmark が入る |
| **2** | 段階1の最小版（§4.2 の要件1〜7 のうち C に関わるもの） | 誤分類が消える（before/after を測る） |
| **3** | L3a の受け口 ＋ レポート5「解決サマリ」 | **最初に作るレポートは 5**。§2.3 が出力の一部になる |
| **4** | レポート1〜4 | cJSON / cmark で 5 レポートが出る |
| **5** | L0（C#）＋ F-16 決定2・決定3 | 列を増やさずに FluentValidation が載る |

**段3 でレポート5 を先に作る**のは順序の問題ではなく原則の問題である。
解決サマリが無い状態で図を出すと、その時点で §2.3 に反する。

### 6.3 テスト

| 層 | 方法 |
|---|---|
| 理解層（L3a） | **ゴールデンデータとの比較。** `docs/golden/*.tsv`（突合キーは `(file, start_line, start_col, kind)`、対象コミット固定） |
| 検出層（L3b） | 真陽性コーパス／偽陽性コーパス |

**この2つを同じテストスイートに混ぜない。** 片方を通すためにもう片方を壊す改変が起きる（[構想] §7.3）。

対象プロジェクトは [構想] §8.3 の推奨セット。`targets/` はリポジトリに取り込まない。

> **shallow clone では git の変更頻度が測れない**（全ファイル一律 1 件になる）。
> §8.3 の推奨セットはすべて shallow clone で取得しているため、レポート3 の検証には
> full clone が要る。

## 7. 限界と未検証

### 7.1 簡易版の天井（原理的に届かない）

| 届かないもの | なぜ |
|---|---|
| チェーン呼び出し（`a.b().c()`）と `var` | 本物の型推論が要る（段階5）。C# では改良後も `needs_type` が 408 件残る |
| 呼び元の網羅 | 閉世界仮定の外を保証できない |
| 実装への到達（インタフェース経由） | 到達先は宣言で止まる。フル版でも仮想ディスパッチは別途解決が要る |
| マクロ展開後のコード | tree-sitter はプリプロセッサを解決しない |

### 7.2 未検証のまま進める項目（**後回しと明示する**、F-16 決定5）

②-a の的中率は**すべての比率の土台**だったので測った（§3.3）。**残る4件はその性質を持たないので後回しにする。**

| 項目 | 状態 |
|---|---|
| テンプレート・マクロを多用した**実際の** C++ で構文木がどこまで壊れるか | 合成コードでは確認済み。実プロジェクトは未 |
| 実プロジェクトでの関数一覧の取りこぼし率 | 未測定 |
| **②-b の誤結線率** | 未測定。ただし ②-b は L0 で線を引かないので L1 は汚れない |
| **段階1の実装コスト** | 未測定（§6.1 のとおり着手順の判断はブロックしない） |

**`resolved_by` のうち `macro` / `stdlib_dict` の的中率も未測定。**
`self_receiver` は §4.2 要件7 の修正後に測り直す。

> **「未検証」と書いてあること自体が出力の一部である。** §2.3 の「不確かさを黙って隠さない」は
> データだけでなく、この文書にも適用する。

### 7.3 第2段（初版に入れない）

**Go / Rust / Java は、初版で持つ3列（`via_lambda` / `comments.source_kind` /
`symbols.visibility_source`）の亜種にしかならない見込み**なので第2段でよい。
各言語の抽出器の設計も第2段。
