# レポートの仕様（L3a）

**版**: 0.1（2026-08-31）
**位置づけ**: L1 のファクトから人が読むものを作る層の仕様。

> **前提**: `SPEC.md` §3 **規則4** —「解析側とアプリ側を L1 で切り、アプリは後から足せる形にする」。
> **5レポートは初版の最小セットであって、出せるものの上限ではない。**

---

## 1. プラグインの受け口

### 1.1 配置と登録

| 項目 | 規約 |
|---|---|
| 配置 | `core/views/<id>.py`。**1ファイル1レポート** |
| 登録 | 本体が `core/views/` を走査し、**`REPORT` を公開しているモジュールを採用する** |

**ファイル名で判定しない。** 名前を変えると壊れるが、`REPORT` の有無で判定すれば壊れない。
利用者が自分のレポートを足すときも、ファイルを置くだけで済む。

### 1.2 `REPORT` の形

```python
REPORT = Report(
    id="resolution-summary",         # 一意。CLI の `report <name>` で指定する名前
    title="解決サマリ",
    requires=[...],                  # §1.5
    formats=["md", "html"],          # 対応する出力形式。既定は先頭
    render=render,                   # §1.3
)
```

### 1.3 `render` の署名

```python
def render(conn: sqlite3.Connection, ctx: Context, fmt: str) -> list[Artifact]:
    ...
```

| 引数 | 中身 |
|---|---|
| `conn` | **読み取り専用で開いた L1 への接続** |
| `ctx` | `analysis_run` の内容、`scope`、`extractor` / `snapshot` の絞り込み値、上限値 |
| `fmt` | 出力形式 |

**`conn` は読み取り専用で渡す。** レポートが L1 を書き換えられてはならない（規則2・3）。

### 1.4 ★ ORM を挟まない

**入力は生の `sqlite3.Connection` とし、レポートは SQL を直接書く。**

**理由**: L1 が SQLite であることは決定事項であり、**SQL がそのまま資産になる**。
ORM を挟むと `SCHEMA.md` の写しがコード側にでき、**列定義の写しが増えて追随漏れが起きる**——
これは過去に実際に起きた失敗（写しが5箇所にあり、うち1箇所が「3テーブル」のまま取り残された）で、
`SCHEMA.md` を唯一の正本にすることで潰した問題である。**再発させない。**

### 1.5 `requires` — 前提が欠けたら**描かずに理由を出す**

レポートが必要とする条件を宣言する。

```python
requires=[
    NeedsTable("refs"),
    NeedsColumn("files", "commit_count"),
    NeedsGitState("full", "shallow"),   # git_state='none' では描けない
]
```

**満たさないときの振る舞い**:

| してよいこと | してはならないこと |
|---|---|
| **描かずに、何が欠けているかを出す** | **黙って軸を減らして描く** |

> **具体例**: `git_state='none'`（zip を展開しただけのツリー）では
> レポート3「ホットスポット」の4軸のうち**「変更頻度」が消える**。
> **黙って3軸で描くと、利用者にはそれと分からない。**

`list-reports` はこの充足状況を一覧する。

### 1.6 出力は `Artifact` を**返す**

```python
Artifact(name="resolution-summary.md", media_type="text/markdown", content=b"...")
```

**レポートがファイルシステムに触ってはならない。** 書き込むのは本体である。

**理由**: 出力先の規約が散らないこと。そして**同じレポートを別の出口へ流せる**こと——
将来のローカル Web UI は、ファイルを読むのではなく `Artifact` を直接受け取る。

## 2. 描画手段

**Mermaid と単一 HTML の両方を持つ。排他にしない。**

| 手段 | 位置づけ | 理由 |
|---|---|---|
| **Mermaid**（テキスト） | **既定** | 依存ゼロ。テキストなので **diff が取れる**。GitHub やエディタでそのまま見える |
| 単一 HTML | 併存 | 大きいグラフで Mermaid が破綻する。対話が要る。将来の Web UI と地続き |

> **「Mermaid か自作 HTML か」は答えるべき問いではなかった。**
> プラグイン形式にする以上、両方を別プラグイン（または同一レポートの `formats`）として持てる。

### 2.1 禁止事項

**外部バイナリを要求する手段（Graphviz など）は採らない。** `SPEC.md` §2.1 に違反する。

HTML が使う JS / CSS は**同梱する**。実行時にネットワークから取得してはならない。

## 3. 規模の戦略

**実測**: 解決済みの呼び出しは cJSON **350 本** / cmark **827 本**。
**Mermaid は数百ノードで実用外になる。**
一方でコンポーネント粒度の図は C# で **6 本**だった——**効くのは C のコールグラフ側**である。

| 規則 | 内容 |
|---|---|
| 既定の粒度 | **コンポーネント（ディレクトリ／名前空間）**。関数粒度は `scope` 指定時のみ |
| 上限超過時 | 全部描かず「上位 N のみ」に落とす |
| **必ず併記** | **省略した件数と基準** |

**間引いた図を、網羅した図として見せてはならない。**

## 4. 5レポートの定義

**すべてのレポートは、冒頭に `analysis_run` の内容（どの境界で走ったか）を出す。**
「呼び出しの 66% が確定」は前提つきの数字だから。

### レポート5「解決サマリ」— **最初に実装し、最初に見せる**

| | |
|---|---|
| **目的** | **何がどれだけ確からしいかを最初に示す。** これが無い状態で図を出してはならない |
| **中核** | `refs` を `status` / `reason` / `dispatch` / `confidence` / **`resolved_by`** で集計する |
| **必ず含める** | ① `analysis_run` の内容 ② **`resolved_by` ごとの内訳** ③ **`files.error_lines > 0` のファイル一覧** |
| `requires` | `refs` |

**`resolved_by` ごとの内訳が要る理由**: 的中率が規則ごとに **25% 〜 100%** とばらけるため、
`resolved` の総数だけでは確からしさが伝わらない。

**ERROR のあるファイルを列挙する理由**: 括弧の不均衡でシンボルが1つも取れなかった場合、
**`confidence` を下げる対象の行が存在しない**。ファイル単位で出すしかない。

### レポート1「概観」

| | |
|---|---|
| **目的** | ディレクトリ別のファイル数・行数・言語構成 |
| **中核** | `files` をディレクトリで集約 |
| `requires` | `files` |

### レポート2「機能の見取り図」

| | |
|---|---|
| **目的** | **「どのフォルダに何の機能があるか」への直接の答え** |
| **中核** | ディレクトリ／名前空間ごとに、**ファイル先頭コメント＋主要シンボルの doc** を集約する |
| `requires` | `comments`、`symbols` |

**このレポートが簡易版の主力である。**
doc コメントは「この関数が何をするか」を人が書いた唯一の記述で、**名前解決を一切必要としない**。
実測では doc を持つ定義が cJSON 34.2% / cmark 22.6% / FluentValidation 49.8%、
ファイル先頭コメントは FluentValidation で **130/137 ファイル**にあった。

> **`source_kind` を無視しないこと。** Python の docstring は文字列リテラルであり、
> コメントノードだけを見ると**定義の 65% を取りこぼす**。

### レポート3「ホットスポット」

| | |
|---|---|
| **目的** | **「どこから読むか」の答え** |
| **中核** | 規模 × **変更頻度（git）** × 分岐数 × **doc の欠落率** |
| `requires` | `files`、`symbols`、`comments`、**`git_state` が `full` または `shallow`** |

**分母・分子は `COUNT(DISTINCT id)` を使う。** 条件コンパイルの枝を分母から除外しない
（除外すると `#ifdef` の多いファイルで水増しが起きる）。

> **`git_state='shallow'` では変更頻度が全ファイル一律 1 になる。** 警告を出すこと。

### レポート4「コンポーネント依存」

| | |
|---|---|
| **目的** | ディレクトリ／名前空間の単位に呼び出しを集約した図 |
| **中核** | `refs` の `status='resolved'` を、src / dst のコンポーネントで集約 |
| `requires` | `refs`、`symbols` |
| **必須の併記** | **集約前の `status` 分布**（＝レポート5 の要約） |

**C も C# も出せる。** ただし**乗る割合は言語で大きく違う。**

| | C#（FluentValidation、初版の構成） |
|---|---|
| エッジを持つコンポーネント | 6 中 **5** |
| コンポーネント間エッジ | 6 種 / **94 件** |
| **全呼び出しに対する割合** | **9.2%** |

> **94 本で描いた図を、網羅した図として見せてはならない。**
> 最大の 1 本（63 件）を除くと残り **31 件**しかなく、図の形は少数のエッジに支配されている。
> **集約はノイズを減らすが、欠落は埋めない。**

## 5. 出力先

| 項目 | 規約 |
|---|---|
| 既定 | `out/<report-id>.<ext>` |
| 上書き | `--out <dir>` |
| 索引 | `out/index.md`（または `.html`）に**生成したレポートの一覧と、描かなかったレポートとその理由**を出す |

**描かなかったレポートを索引から省いてはならない。** 「無い」ことが分からなくなる。

---

## 6. 初版に含めないレポート

後から足せる。**足すときは本体を触らずファイルを1つ置くだけで済むこと**が §1 の要件である。

命名の語彙集計 ／ 型参照 ／ 継承関係 ／ コメントアウトされたコードの判定
（FluentValidation で 146 件の候補が出たが、判定はヒューリスティックなので L3a の領分）。
