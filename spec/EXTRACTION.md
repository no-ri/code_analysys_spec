# 抽出と解決の仕様（L0）

**版**: 0.1（2026-08-31）
**位置づけ**: **実装の本体。** 「ソースツリーから `SCHEMA.md` の各行をどう作るか」を定める。

> **本書が要る理由**: 「どう解くか」は従来、決定の記録に分散し、
> **実際の判定順序は測定スクリプトの中にしかなかった**。その結果、
> **3つのスクリプトが同じ判定を別々に書き直し、同じ指標が 53 / 55 / 56 と食い違った。**
> **判定規則を1箇所に書き下ろすのが本書の役目である。**

---

## 1. 入出力

| | |
|---|---|
| **入力** | ソースツリー（1つ以上）。ビルド成果物・設定ファイルは**一切要求しない** |
| **出力** | `SCHEMA.md` の 5 テーブルを満たす行 |
| **使う道具** | tree-sitter の構文木のみ。**コンパイラ・型チェッカは使わない** |

**抽出は S 式クエリで書く。** Python 側で木を全走査すると実測で約9倍遅い
（1.7MB / 20,000行の C で 2.37 秒 → クエリなら 0.26 秒）。

---

## 2. 用語

| 語 | 意味 |
|---|---|
| **閉世界仮定** | 解析対象のツリー（＋追加ツリー）がプログラムの全体であるとみなす仮定 |
| **定義表** | リポジトリ全体から集めた「名前 → 定義」の索引。**解決フェーズの入力** |
| **束縛** | その関数・ファイル内で、変数・引数・プロパティとして名前が値に結び付けられていること |
| **container** | シンボルを囲むもの（C はファイル、C# は名前空間 → 型） |
| **自己参照語** | レシーバのうち「自分自身」を指す語（C# は `this`） |
| **基底参照語** | レシーバのうち「基底型」を指す語（C# は `base`） |

## 3. 抽出フェーズ（ファイル単位・判断しない）

**このフェーズでは解決しない。** 1ファイルの構文木だけで分かる事実を出す。

### 3.1 `files`

行数、コメント行数、**ERROR ノード数**、`lang`、`extract_status`、git メトリクス。

**`lang` の決め方**: 拡張子で一意なら `confidence='high'`。`.h` のように複数言語がありうる拡張子は
`medium`。内容から推測した場合は `low`。

### 3.2 `symbols`

定義されたものを出す。**宣言と定義を区別する**（`is_definition`）。

| 言語 | container の鎖 |
|---|---|
| C | ファイル → 関数 / マクロ |
| C# | **名前空間 → 型 → メソッド** |

**C# の file-scoped namespace（`namespace X;`）を必ず扱う**（`SPEC.md` §9 要件3）。
ブロック形式（`namespace X { }`）だけを見ていると名前空間が ID から欠落する。

シンボルIDの組み立ては `SCHEMA.md` §2.6。**descriptor にパラメータの型名リストを含める**
（省くと C# で 17.7% が衝突して消える）。

**無名関数（ラムダ）は `symbols` に登録しない。** ID が位置ベースになり、
1行ずれただけで別物になる。代わりに `refs.lambda_depth` で「ラムダの中からの呼び出し」を表す。

### 3.3 `comments`

**「コメント構文」ではなく「人が書いた説明」を集める。**
C / C# はコメントノードだが、**Python の docstring は文字列リテラル**である
（`source_kind` で区別する）。

`kind='doc'` の紐付けは慣習に基づく判断なので、**位置は事実として必ず記録し、
紐付けは `confidence` つきで別に持つ**（L3a で再計算できるように）。

### 3.4 `refs`（生の収集）

**この時点では解決しない。** 呼び出し式・import 文・変数参照を**式のまま**拾う。

| 拾うもの | `kind` |
|---|---|
| 呼び出し | `call` |
| `#include` / `using` / `import` | `import` |
| 変数の読み書き | `var_read` / `var_write` / … |

`dst_expr` に**元の式をそのまま**入れる（`fp`、`handler->on_event`、`a.b().c()`）。

## 4. 定義表の構築（全ファイル読み込み後）

**解決フェーズの前に、リポジトリ全体の定義表を作る。**

| 索引 | 内容 |
|---|---|
| `by_name` | 名前 → 定義のリスト（ファイル、container、可視性、シグネチャ） |
| `by_container` | (container, 名前) → 定義。**基底型の鎖も辿れるようにする** |
| `types` | 型名 → 定義。`container` の解決に使う |
| `macros` | 関数形式マクロの名前 → 定義 |
| `bases` | 型名 → 基底型名のリスト |

**追加ソースツリー（境界レベル1）の定義も同じ表に入れる。** ただし `repo-name` が違うので
`dst_id` の接頭辞で区別でき、「追加ツリーのおかげで解けた行」は後から引ける。

> **1ファイルずつ解決してはならない。** 他ファイルの定義が見えず `external` を誤って出す。

### 4.1 束縛の収集（ファイル単位）

解決フェーズで使うため、ファイルごとに次を集める。

| 集合 | 中身 |
|---|---|
| `bound` | 変数・引数・プロパティとして束縛された名前 |
| `declared` | 名前 → **ソースに書かれた宣言型**（型推論に頼らない。`var` は含めない） |

**`declared` の型名は正規化する**（`?` を外す、総称型引数を落とす、`[]` を外す、
修飾名は最後の要素を取る）。

## 5. 解決フェーズ — **判定手順**

### 5.1 呼び出し式の分類

| 形 | 例 |
|---|---|
| **識別子** | `foo(x)` |
| **メンバ** | `obj.foo(x)`、`p->foo(x)`、`Type.foo(x)` |
| **間接** | 関数式が識別子でもメンバでもない（`fp()`、`(*f)()`、`a.b().c()` の外側） |

### 5.2 判定順序

**上から順に当て、最初に当たったもので確定する。**

```
関数式が識別子でもメンバでもない
  → 間接呼び出し（§5.5-A）

【識別子の場合】
  1. macros に一致                     → resolved  resolved_by=macro          dispatch=macro
  2. bound に含まれ、かつ by_name に定義が無い
                                       → 間接呼び出し（§5.5-A）
  3. 囲む container（基底の鎖を含む）に同名の定義
                                       → resolved  resolved_by=same_container
  4. 同一ファイルのファイルローカル定義（C の static 等）
                                       → resolved  resolved_by=same_file_static
  5. by_name の候補が 1 件             → resolved  resolved_by=unique_in_repo
  6. 候補が 0 件 → 標準ライブラリ辞書に一致（§6）
                                       → unresolved reason=external  resolved_by=stdlib_dict  dst_id あり
  7. 候補が 0 件（辞書にも無い）       → unresolved reason=external  resolved_by=not_resolved
  8. 候補が 2 件以上                   → unresolved reason=ambiguous resolved_by=not_resolved

【メンバの場合】レシーバ recv / メソッド名 mn
  1. recv が自己参照語（this / self）  → 囲む型から探す（基底の鎖を含む）
                                          見つかれば resolved  resolved_by=self_receiver
  2. recv が基底参照語（base / super） → ★ 囲む型を除外し、基底の鎖だけから探す（§5.3）
                                          見つかれば resolved  resolved_by=self_receiver
                                          見つからなければ unresolved reason=external
  3. recv が types にある型名          → その型から探す（基底の鎖を含む）
                                          見つかれば resolved  resolved_by=type_name_static
  4. recv が declared にあり、その型が types にある
                                       → その型から探す（基底の鎖を含む）
                                          見つかれば resolved  resolved_by=declared_type
  5. recv が declared にあり、その型が types に無い
                                       → unresolved reason=external
  6. それ以外                          → unresolved reason=needs_type

【共通・最後に必ず適用】
  resolved になった行について、到達先の候補が 2 件以上（オーバーロード）なら
    → unresolved reason=ambiguous へ降格（§5.4）
```

**手順3 を手順4 より先に置く理由**（識別子の場合）: C# は `this.` を省略できるので、
囲む型のメソッドが最優先で当たる。**この順序を入れ替えると、同名の他クラスのメソッドを誤って指す。**

**手順4 を手順5 より先に置く理由**: C の `static` は同一翻訳単位が勝つという**言語規則**である。
リポジトリ内に同名の `static` が2つあっても、同一ファイルのものが正しい（実測 25/25）。

### 5.3 ★ 基底参照語（`base.`）は囲む型を**除外**して探す

**`base.X()` は「自分の型を飛ばして基底から探す」という意味である。**

自分の型を含めて探すと、**override しているメソッドは必ず自分自身に当たる**。
構造上かならず外し、しかも**偽の自己再帰エッジ**を作ってコールグラフの形を歪める。

> **実測**: FluentValidation の `base.` 呼び出しは 2 件で、**2 件とも誤っていた**（的中率 0%）。
> `IncludeRule.cs:70 base.ValidateAsync` は基底 `PropertyRule<T,T>.ValidateAsync` が正しいのに
> 自分自身を指し、`ValidationException.cs:92 base.GetObjectData` は基底が `System.Exception` なので
> 正しくは `external` なのに自分自身を指していた。

**基底がリポジトリ外なら `external` にする。** 自分自身に落とさない。

### 5.4 ★ オーバーロードは `resolved` にしない

**到達先の候補が 2 件以上あるなら、名前一致では一意に決まらない。**
`status='unresolved'` / `reason='ambiguous'` に降格する。

> **これは `confidence` を下げる話ではない。** 「解決できたがあまり信じられない」ではなく
> **「解決できていない」が実態**だから、`status` を降格するのが正しい。

**実測**: C# の誤り 22 件のうち **20 件がオーバーロードの取り違え**だった。
`SetValidator` は 4 オーバーロードあり、常に同じものを指していた（15 件すべて誤り）。

降格の効果:

| | 件数 | 全呼び出し 1,022 件に対して |
|---|---:|---:|
| 降格前の `resolved` | 325 | 31.8% |
| うち実際に正しい（推定） | 215.5 | **21.1%** |
| **降格後の `resolved`** | **204** | **20.0%** |

**20.0% と 21.1% はほぼ一致する。** 降格は数字を下げる措置ではなく、**名乗りを実態に合わせる措置**である。

#### 引数の個数で絞ろうとしないこと

**実測で効かない。** オーバーロードのある 121 件のうち **117 件（96.7%）は仮引数の個数がすべて同じ**で、
個数で絞れる可能性があるのは **4 件だけ**だった（`params` と省略可能引数があるため）。

**絞るなら実引数の形と宣言型を見る**（`new X(...)` か、ラムダか、識別子ならその宣言型か）。
ただし**部分的にしか効かない**ので、**絞れなかったものは `ambiguous` に落とす**のが前提である。

### 5.5 列の埋め方

#### A. 間接呼び出し

| 列 | 値 |
|---|---|
| `status` | `unresolved` |
| `reason` | `needs_dataflow`（どの関数が代入されたかはデータフロー解析が要る） |
| `dispatch` | `function_pointer` |
| `resolved_by` | `not_resolved` |

#### B. `resolved` の行

| 列 | 値 |
|---|---|
| `status` | `resolved` |
| `reason` | **空**（`reason` は障害専用） |
| `dst_id` | 到達先のシンボルID |
| `dispatch` | `direct` / `virtual` / `macro` |
| `resolved_by` | §5.2 で確定した規則 |
| `confidence` | **`resolved_by` ごとに決める**（`SCHEMA.md` §6） |

#### C. `confidence` は `resolved_by` ごとに決める

**②-a を一律 `medium` にしてはならない。** 的中率を規則ごとに実測したところ
**25% 〜 100% とばらけた**。

| `resolved_by` | 実測的中率 | `confidence` |
|---|---|---|
| `same_file_static` / `unique_in_repo` | 100%（C 50/50、C# 4/4） | `medium` |
| `type_name_static` | 95%（19/20） | `medium` |
| `same_container` | 80%（16/20） | `medium` |
| **`declared_type`** | **25%（5/20）** | **`low`** |
| `self_receiver` | 0%（2/2）※ **§5.3 の修正前の値** | **暫定 `low`。修正後に測り直す** |
| `macro` / `stdlib_dict` | 未測定 | `medium` |

> **`declared_type` が低い理由**: 宣言型がインタフェースのとき、呼んでいるメソッドが
> 拡張メソッドや外部の基底にあり、**宣言型からは見つからない**。
> 誤りの大半は §5.4 のオーバーロード降格で消えるが、**残りは `low` として扱う**。

## 6. 標準ライブラリ辞書

**`external` を「既知の標準ライブラリ」と「未知の外部」に分ける。**

| 状態 | `dst_id` | `status` | `reason` | `resolved_by` |
|---|---|---|---|---|
| 既知の標準ライブラリ | **`c-stdlib c99 - printf().`** | `unresolved` | `external` | `stdlib_dict` |
| 未知の外部 | 空 | `unresolved` | `external` | `not_resolved` |

### 6.1 `resolved` に格上げしない

格上げすると C の解決率が 66.5% → 8割超に跳ね上がるが、**コードについて分かったことは1つも増えていない**——
名前が libc のリストに載っていた、というだけである。**数字だけが良くなるのは `SPEC.md` §1.1 に反する。**

`external` のまま残った呼び出しの集計は「**このプロジェクトが依存する外部 API の一覧**」であり、
一次解析には十分に有用である。

### 6.2 誤爆しない理由

**辞書を引くのは、リポジトリ内に候補が 0 個のときだけ**（§5.2 手順6）。
自前で `open()` を定義していればそちらが先に解決されるので発火しない。

### 6.3 辞書はコードではなくデータ

`data/` に置き、**バージョンを持たせる**（`c99` / `posix` / `python-3.12-builtins`）。
使った辞書とバージョンは `analysis_run.stdlib_dicts` に記録する。

## 7. `import` の解決

| 言語 | 対象 | 解決 |
|---|---|---|
| C | `#include "x.h"` | **相対パスを解決してリポジトリ内のファイルを指す**（`SPEC.md` §9 要件5） |
| C | `#include <x.h>` | システムヘッダ。`external` |
| C# | `using X.Y;` | 名前空間。リポジトリ内に該当があれば指す |

**実測の注意**: 内部依存は思ったより少ない。
FluentValidation の `using` は **241 件すべて `System.*`**（単一名前空間のため内部 `using` が存在しない）、
C の `#include` でリポジトリ内を指すのは **3 件のみ**だった。
**`import` から内部依存図を描こうとしてはならない。**

## 8. 言語ごとに変わるもの — **これだけ**

**判定の骨格（§5.2）は言語で変えない。変えるのは集合の中身だけ。**

| 集合 | C | C# | （参考）Python | （参考）JS |
|---|---|---|---|---|
| **自己参照語** | — | `this` | `self` / `cls` | `this` |
| **基底参照語** | — | `base` | — | `super` |
| ファイルローカルの印 | `static` | — | — | — |
| container の鎖 | ファイル | 名前空間 → 型 | モジュール → クラス | モジュール → クラス |
| doc の担い手 | コメント | コメント | **文字列リテラル** | コメント |

> **この表が要る理由**: かつて 6 言語を1つの表で扱うために自己参照語を**全言語の和集合**にした結果、
> **C# の `base` を入れ忘れ**、`base.X()` を 2 件取りこぼした。
> **和集合方式は「どの言語で何が抜けたか」が見えない。** 言語ごとに明示する。

## 9. ERROR ノードの扱い

tree-sitter は壊れたコードからも木を返すが、**黙って痩せた結果を返す**。

| 入力 | 実測 |
|---|---|
| 式の破損、未知のマクロ修飾 | **完全に回復**（3/3） |
| **括弧の不均衡** | **後続を巻き込んで全滅**（0/3。関数を1つも拾えない） |

### 9.1 必ず数え、必ず記録する

`files.parse_errors`（件数）と `files.error_lines`（ERROR が乗った行数）を記録する。

### 9.2 `confidence` への反映

| 対象 | 規則 |
|---|---|
| `symbols` | **範囲全体**が基準。範囲内に ERROR があれば `medium`、支配的なら `low` |
| `comments` | ERROR ノードと同じ行／隣接行なら `low` |

### 9.3 欠落は `confidence` では表せない

**括弧の不均衡でシンボルが1つも取れなかった場合、下げる対象の行が存在しない。**
`files.error_lines` に記録し、**レポートでファイル単位に列挙する**（`REPORTS.md` レポート5）。
