# 仕様書 — 簡易版ソースコード解析ツール

**版**: 0.1（2026-08-31）
**位置づけ**: **`spec/` 一式だけで実装に着手できること**を条件とする。
本書は `DECISIONS.md`（別リポジトリ）を読まなくても実装できるように書く。根拠が要る箇所は出典を注記する。

| 本書の外にあるもの | 場所 |
|---|---|
| 列の定義・値域・主キー・DDL | **`SCHEMA.md`** |
| 呼び出しの解決手順（実装の本体） | **`EXTRACTION.md`** |
| レポートのプラグイン仕様と5レポート | **`REPORTS.md`** |
| ゴールデンデータと受け入れ基準 | **`TESTING.md`** |

## 1. 何を作るか

ソースツリーを読み、**構造化データ（ファクト）**を SQLite に出し、その上でレポートを生成する CLI。

**想定用途は「初見のソースコードの一次解析の補助」。** 網羅的な正確さではなく全体像の把握が目的。

### 1.1 貫く原則 — これに反する実装は誤り

> **間違った答えが自信を持って出るツールは有害である。**

この原則は本書の随所で具体的な要件になる。迷ったときは次の順で判断する。

1. **解けないものを解けたことにしない**（`status` を降格する）
2. **黙って劣化させない**（前提が欠けたら理由を出す）
3. **数字には前提を添える**（どの境界で走ったか、何を間引いたか）

**解決率を上げることより、名乗りを実態に合わせることを優先する。**

### 1.2 対象言語

**初版は C と C#。** C から実装し、5レポートを通してから C# を載せる。

**列を1つも増やさずに両言語が同じテーブルに載ることは実測済み。**
言語固有の概念は汎用語彙へ写す（`static`/`extern` と `public`/`internal` は `visibility` に、
名前空間と型は `container_id` に）。

抽出器を持たない言語のファイルは `files` に行だけ立て、`extract_status = 'skipped_no_extractor'` とする。

## 2. 動作の前提 — 利用者に何を要求するか

**この2つが本ツールの存在理由なので、実装で崩してはならない。**

| 軸 | 要求 |
|---|---|
| **軸1: 利用者のマシン** | **Python 3.10+ と `pip install` 1コマンドだけ** |
| **軸2: 解析対象** | **ゼロ。** ソースツリーが読めればよい |

### 2.1 軸1 の具体的な制約

- 実行時依存は **`tree-sitter` と `tree-sitter-language-pack` のみ**（どちらも `Requires-Python >= 3.10`）
- `sqlite3` は Python 本体に同梱。**追加インストールしない**
- **外部バイナリを要求してはならない**（Graphviz、cmake、dotnet、node など）
- レポートが使う JS 等は**同梱する**（実行時にダウンロードしない）

### 2.2 軸2 の具体的な制約

**次のものを起動条件にしてはならない。**
`compile_commands.json` / `.sln` / `.csproj` / `tsconfig.json` / `node_modules` / 依存パッケージの入った実行環境。

**ビルドが通らないリポジトリ、zip を展開しただけのツリー、一部だけのソースが、そのまま対象になる。**

### 2.3 閉世界の境界はパラメータ

軸2 = ゼロは**既定値であって二択ではない**。追加のソースツリーを渡せるようにする。

| レベル | 渡すもの | 到達できるもの |
|---|---|---|
| **0** | 何も渡さない | 解析対象ツリーの中だけ（**既定**） |
| **1** | 追加ソースツリー（別の `repo-name` を持つ） | 定義まで |
| 2 | システムヘッダ | — **実装しない**（下記） |
| 3 | ビルドコンテキスト | — 簡易版では実装しない |

> **レベル2 を実装しない理由**: `/usr/include/stdio.h` で実測したところ、`extern` 宣言 138 行に対し
> 抽出できた関数宣言は **16 件のみ**（ERROR ノード 136）。`__THROW` / `__nonnull` 等の属性マクロで
> 宣言ごと ERROR に落ちる。**システムヘッダは tree-sitter が最も苦手な入力**であり、
> 代わりに**標準ライブラリの名前辞書**を持つ（`EXTRACTION.md` §6）。

**どの境界で走ったかは `analysis_run` に必ず記録する。**
記録が無いと `external` という同じ語が実行ごとに別のことを指す。

## 3. 層と、層をまたがせない規則

```
L0  抽出層 (extractors/)   事実のみを出す。判断しない。捨てない。
                           ↓ 追記のみ
L1  ファクト層 (facts/)    スキーマ固定。信頼度つき。不変。   ← 唯一の境界
                           ↓ 派生（再生成可能）
L2  派生層 (derived/)      到達可能性、推移閉包など
                  ┌────────┴────────┐
L3a 理解層 (views/)        L3b 検出層 (rules/)
    図、レポート、検索          ルール評価 → findings
```

### 規則1: L0 に判断ロジックを一切入れない

「このパターンは怪しい」「これはテストコードだろう」という**知識は L0 に置かない**。
抽出器は「見たものを記録する」だけ。

**具体例**: テスト／生成コード／vendor の判別は L0 でやらない。
`files` にパスと事実（マーカーコメントの有無）を記録し、**判定は L3a で行う**。

### 規則2: フィルタリングは下流でのみ行う

精度を上げたければ `WHERE status='resolved' AND confidence='high'` のように**クエリ側で絞る**。
**抽出器で絞らない。**

### 規則3: findings は別テーブル・別ライフサイクル

L1 と混ぜない。ルールを消せば findings も消える関係を保つ。**L1 は L3b の存在を知らない。**

### 規則4: 解析側とアプリ側を L1 で切り、アプリは後から足せる形にする

**L1 を唯一の境界とし、その上下を独立に差し替えられるようにする。**
L3a（図・レポート）は L3b のルールと同じく**プラグイン形式**にする（→ `REPORTS.md`）。

> **理由**: 取得したデータから何を読み出すかは、**実際のデータを見て初めて思いつく**。
> 最初から決め打ちにすると、自前でファクトを持つ意味——後から自由に問いを立てられること——が失われる。
> **5レポートは初版の最小セットであって、出せるものの上限ではない。**

## 4. 実装構成

### 4.1 要件

| # | 要件 | 理由 |
|---|---|---|
| 1 | **ロジックは `core/` に置き、CLI は薄いラッパーにする** | GUI を後から安く足せるようにする |
| 2 | **ジョブ設定ファイル（TOML）を持つ** | 同上。CLI 引数だけにしない |
| 3 | **進捗を構造化して出力する** | 同上。人間向けの文字列だけにしない |
| 4 | **抽出器は独立プロセスとして起動できる** | 言語ごとに差し替えられるようにする |
| 5 | **判定規則は1箇所に置く**（§6.3） | 同じ判定を複数箇所に書くと食い違う（実績あり） |

### 4.2 想定するディレクトリ

```
core/          ロジック（CLI から独立して呼べる）
  extractors/  L0：言語別の抽出器
  facts/       L1：スキーマ定義とローダ
  derived/     L2
  views/       L3a：レポートプラグイン（1レポート1ファイル）
  rules/       L3b：検出ルール（1ルール1ファイル）
cli/           薄いラッパー
data/          標準ライブラリ辞書など
```

**`views/` と `rules/` はプラグインの置き場**であり、本体はここを走査して読み込む（→ `REPORTS.md` §1）。

## 5. CLI

### 5.1 コマンド

| コマンド | すること |
|---|---|
| `analyze <path>` | L0 → L1。ファクトを DB に書く |
| `report <name\|all>` | L1 → L3a。レポートを生成する |
| `run <path>` | `analyze` と `report all` を続けて実行する |
| `list-reports` | 登録されているレポートと、その `requires` の充足状況を出す |
| `verify` | DB がスキーマどおりか、整合しているかを確かめる |

### 5.2 主な引数

| 引数 | 既定 | 意味 |
|---|---|---|
| `--db <path>` | `facts/db.sqlite` | L1 の実体 |
| `--out <dir>` | `out/` | レポートの出力先 |
| `--extra-root <name>=<path>` | なし | 境界レベル1。**複数指定可** |
| `--no-closed-world` | 閉世界仮定あり | 仮定を外す（`resolved` が減る） |
| `--config <path>` | `analysis.toml` | ジョブ設定ファイル |
| `--jobs <n>` | CPU 数 | 並列度 |
| `--format <fmt>` | プラグインの既定 | `report` の出力形式 |

**CLI 引数と設定ファイルは同じ項目を表す。** 優先順位は **CLI 引数 > 設定ファイル > 既定値**。

### 5.3 終了コード

| コード | 意味 |
|---|---|
| 0 | 正常 |
| 1 | 利用者の誤り（パスが無い、設定が不正） |
| 2 | **処理は完了したが、一部の抽出器が失敗した**（`files.extract_status` に残る） |
| 3 | 内部エラー |

**2 を 0 にしない。** 静かに部分的な結果を返すのは §1.1 の原則に反する。

## 6. 処理フロー

### 6.1 `analyze`

```
1. 対象ファイルを列挙する（除外規約は §6.2）
2. analysis_run に1行書く（境界レベル、追加ツリー、辞書、ツール版、開始時刻）
3. ファイルごとに:
     a. パースする
     b. ERROR ノードを数える → files.error_lines / parse_errors
     c. symbols / comments を抽出する（判断しない）
     d. 呼び出し・参照を「式のまま」拾う（まだ解決しない）
4. 全ファイルの symbols が出そろってから、refs を解決する（→ EXTRACTION.md）
5. L1 へ取り込む（増分なら旧世代を消してから入れる）
```

**手順4 を手順3 と混ぜてはならない。** 解決にはリポジトリ全体の定義表が要る。
**1ファイルずつ解決すると、他ファイルの定義が見えず `external` を誤って出す。**

### 6.2 対象ファイルの除外

除外するディレクトリ名（パス要素として一致）:
`test` / `tests` / `fuzz` / `example` / `examples` / `sample` / `samples` /
`bench` / `benchmark` / `node_modules` / `third_party` / `vendor`

ファイル名に `test` / `bench` を含むもの、`fuzz` で始まるものも除外する。

> **この規約は測定と揃えること。** ゴールデンデータは同じ除外規約で作られている（`TESTING.md`）。
> 除外規約を変えると母集団が変わり、**過去の数字と比較できなくなる**。

### 6.3 増分更新

変更されたファイルだけを再抽出する。**取り込みは「旧世代を消してから入れる」。**

```
for each changed file X:
    DELETE FROM T WHERE file = X AND extractor = ? AND snapshot = ?
    INSERT ...
```

**削除されたファイルの行も消す**（`files` に無いのに `symbols` が残ると幽霊になる）。

> **既知の穴**: ファイル横断の解決結果は、他ファイルが変わると古くなりうる
> （`foo.c` にシンボルを足すと、`bar.c` の `external` が誤りになる）。
> **初版では全体再解決を既定とし、増分は `--incremental` の明示指定でのみ使う。**

## 7. 異常時の振る舞い

**「静かに劣化する」ことを禁じる。** 以下はすべて §1.1 の原則の適用である。

| 状況 | 振る舞い |
|---|---|
| **パースが壊れた** | 木は返るので処理は続ける。ただし **ERROR ノード数を必ず記録**し、`confidence` に反映する |
| **括弧の不均衡で関数が1つも取れない** | **`confidence` では表現できない**（下げる対象の行が無い）。`files.error_lines` に記録し、**レポートでファイル単位に列挙する** |
| **git が無いツリー** | `git_state = 'none'`。`snapshot` は `nogit-YYYYMMDDThhmmss`。**変更頻度を要求するレポートは描かず理由を出す** |
| **shallow clone** | `git_state = 'shallow'`。**変更頻度は全ファイル一律 1 になるので信用しない** |
| **抽出器が言語単位で落ちた** | `files.extract_status = 'failed'` を残し、終了コード 2 |
| **主キーが衝突した** | **黙って捨てない。** エラーとして数え、`analysis_run.load_errors` に記録する |
| **抽出器を持たない言語** | `extract_status = 'skipped_no_extractor'`。`extractor` にはオーケストレータの識別子を入れる |

> **主キー衝突を黙って捨てると何が起きるか**: 実測で、シグネチャ無しのシンボルIDが衝突して
> **C# のシンボルの 17.7% が静かに消えた。** 消えたことは集計を見ても分からない。

## 8. 出力の約束

### 8.1 数字には必ず前提を添える

**「呼び出しの 66% が確定」は前提つきの数字である**——どの境界で走り、閉世界仮定を置き、どの辞書を使ったか。
**`analysis_run` の内容をレポートの冒頭に出す。**

### 8.2 解決サマリを最初に出す

**レポート5「解決サマリ」を最初に実装し、最初に見せる**（`REPORTS.md`）。
順序の問題ではなく原則の問題である——**解決サマリが無い状態で図を出すと、その時点で §1.1 に反する。**

### 8.3 間引いたことを書く

図が大きすぎて間引いた場合、**省略した件数と基準を図と一緒に出す**。

## 9. 初版の必須要件

**「あると精度が上がる」機能ではなく、「無いと嘘をつく」機能である。** 外すと初版として成立しない。

| # | 要件 | 無いとどうなるか | 詳細 |
|---|---|---|---|
| 1 | スコープ解析の最小版 | 関数ポインタ経由の呼び出しを「リポジトリ外の関数」と**誤報告する** | `EXTRACTION.md` §4 |
| 2 | シンボルIDにシグネチャを含める | C# で **17.7%** のシンボルが ID 衝突で**静かに消える** | `SCHEMA.md` |
| 3 | C# の file-scoped namespace 対応 | 名前空間が ID から欠落する | `EXTRACTION.md` §3 |
| 4 | 標準ライブラリ辞書 | `external` を「未知」と「既知」に分けられない | `EXTRACTION.md` §6 |
| 5 | C の `#include` 相対解決 | リポジトリ内の依存が引けない | `EXTRACTION.md` §7 |
| 6 | ERROR ノードの記録 | 取りこぼしが**静かに**起きる | §7 |
| 7 | **`base.` は基底から探す** | 必ず自分自身を指し、**偽の自己再帰エッジ**を作る | `EXTRACTION.md` §5.3 |
| 8 | **オーバーロードは `resolved` にしない** | 到達先が一意に決まらないのに解決済みを名乗る | `EXTRACTION.md` §5.4 |

> **要件1 の採用理由は解決率ではない。** C で測ったところ **`resolved` 率は 0.0 ポイントしか動かないのに、
> 誤分類が 17〜18 件消えた**。§1.1 の原則に直撃するから必須にしている。

## 10. 実装の順序

| 段 | 内容 | 完了の判定 |
|---|---|---|
| **1** | L0（C）＋ L1 ローダ | `SCHEMA.md` の DDL に cJSON / cmark が入る |
| **2** | スコープ解析の最小版（§9 の要件1・5・6） | 誤分類が消える（before/after を測る） |
| **3** | L3a の受け口 ＋ **レポート5「解決サマリ」** | §8.2 |
| **4** | レポート1〜4 | cJSON / cmark で5レポートが出る |
| **5** | L0（C#）＋ §9 の要件2・3・7・8 | **列を増やさずに** FluentValidation が載る |
| **6** | ゴールデンデータでの回帰 | `TESTING.md` の受け入れ基準を満たす |

**C から始める理由**: C は解決の的中率を実測済み（50/50、100%）で**手直しが要らない**。
C# は 66.7% で、要件7・8 の修正を入れてからでないと正しい結果にならない。

## 11. 初版でやらないこと

| やらないこと | 理由 |
|---|---|
| チェーン呼び出し（`a.b().c()`）と `var` の解決 | 本物の型推論が要る |
| 呼び元の網羅 | 閉世界仮定の外を保証できない |
| インタフェース経由の実装への到達 | 宣言で止まる |
| マクロ展開後のコード | プリプロセッサを解決しない |
| 名前一致による推測（②-b） | **L0 で線を引かない。** L2 / L3a の推測モードに置く |
| C / C# 以外の言語 | 第2段 |
| GUI | §4.1 の要件1〜3 で後から足せるようにしておく |
