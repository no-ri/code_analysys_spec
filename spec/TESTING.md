# テストと受け入れ基準

**版**: 0.1（2026-08-31）

---

## 1. テストを2系統に分ける

| 系統 | 対象 | 方法 |
|---|---|---|
| **理解層** | L0 / L1 / L3a | **ゴールデンデータとの比較**（§3） |
| **検出層** | L3b | 真陽性コーパス／偽陽性コーパス |

**この2つを同じテストスイートに混ぜてはならない。**
片方を通すためにもう片方を壊す改変が起きる。

> **精度要件が正反対だから。** 理解層は**再現率**（取りこぼさない、疑わしければ記録する）、
> 検出層は**適合率**（誤検知を出さない、疑わしければ黙る）を重視する。
> 混ぜると閾値の取り合いになり、**抽出器側で怪しいエッジを捨て始める**——
> これがいちばん避けたい失敗である。

## 2. 対象プロジェクト

| プロジェクト | 言語 | 用途 |
|---|---|---|
| **cJSON** | C | **ゴールデンデータの対象**。段1〜4 の主対象 |
| **cmark** | C | 規模の確認（1,381 呼び出し） |
| **FluentValidation** | C# | 段5 の主対象 |
| tinyxml2 / requests / commander.js | C++ / Python / JS | 第2段の参考 |

**`targets/` はリポジトリに取り込まない。** 取得スクリプトで clone する。

### 2.1 ★ shallow clone の落とし穴

**`--depth 1` では git の変更頻度が測れない**（全ファイル一律 1 件になる）。
**レポート3 の検証には full clone が要る。**

## 3. ゴールデンデータ

### 3.1 何が入っているか

`spec/golden/*.tsv`。**②-a（解決できたと主張する行）が実際に正しい先を指しているかを人手で判定した記録。**

| ファイル | 対象 | コミット | 標本 | 正 | 的中率 |
|---|---|---|---:|---:|---:|
| `cjson-2a-sample.tsv` | cJSON [C] | `fb16e5cf358798aabb049655975cde8427101056` | 50 | 50 | **100%** |
| `fluentvalidation-2a-sample.tsv` | FluentValidation [C#] | `daa00b795450881c233253488e3ddeb362f59f56` | 66 | 44 | **66.7%** |

**対象コミットは固定である。** 更新するときは新しいコミットで作り直し、両方を残す。

### 3.2 突合キー

**`(file, start_line, start_col, kind)`。**

**`extractor` と `snapshot` は突合から除く。** 人手で書く正解データではどちらも固定できない
（版が上がる／コミットで変わる）ため。

期待値は `dst_id` / `status` / `reason`。

### 3.3 列

| 列 | 意味 |
|---|---|
| `rule` | どの規則で解いたか。**`refs.resolved_by` に対応する** |
| `claimed_dst_file` / `claimed_dst_line` | ツールが主張した呼び先 |
| `n_overload` | 同名の定義の数。2 以上ならオーバーロード |
| **`verdict`** | **人手判定（`正` / `誤`）** |
| `correct_dst_file` / `correct_dst_line` | `誤` のときの正しい呼び先。**空なら `external`** |
| `note` | なぜ誤りか |

### 3.4 再生成

```sh
python tools/sample-golden.py --lang c      --per-rule 25 --tsv
python tools/sample-golden.py --lang csharp --per-rule 20 --tsv
```

seed は `20260831`。**`verdict` 以降の列は人手で付けたものなので、
再生成すると失われる。** 判定を突合キーで引き継ぐこと。

### 3.5 ★ 標本の限界を数字と一緒に扱う

**規則ごとの標本は 20〜25 件しかない。**
`declared_type` の 25% は **95% 信頼区間で概ね 9〜49%** と幅が広い。

**「`declared_type` は他の規則より明確に低い」は言えるが、25% を確定値として扱わないこと。**

## 4. 受け入れ基準

### 4.1 段ごとの完了判定

| 段 | 完了の判定 |
|---|---|
| 1 | `SCHEMA.md` の DDL をそのまま実行して cJSON / cmark が入る |
| 2 | **誤分類が消える**（before / after を測って示す） |
| 3 | レポート5 が出て、`analysis_run` の内容が冒頭に出る |
| 4 | cJSON / cmark で5レポートが出る |
| 5 | **列を1つも増やさずに** FluentValidation が載る |
| 6 | §4.2 と §4.3 をすべて満たす |

### 4.2 不変条件 — **常に成り立つこと**

CI で毎回確かめる。

| # | 条件 | 破れると何が起きるか |
|---|---|---|
| 1 | 同じ入力を2回流して結果が一致する（`snapshot` 固定） | 再現できない |
| 2 | **主キー衝突が 0 件**（`analysis_run.load_errors = 0`） | 行が静かに消える |
| 3 | `status='resolved'` の行に `reason` が入っていない | 列の役割が濁る |
| 4 | `status='resolved'` の行の `resolved_by` が `not_resolved` でない | 由来が辿れない |
| 5 | **オーバーロードのある到達先を指す `resolved` の行が 0 件** | 到達先が一意でないのに解決済みを名乗る |
| 6 | **基底参照語（`base.`）由来の行が自分自身を指していない** | 偽の自己再帰エッジができる |
| 7 | `symbols` に無名関数の行が無い | ID が位置ベースになり不安定 |
| 8 | `files` に無いファイルの `symbols` / `refs` が無い | 削除されたファイルの幽霊が残る |
| 9 | ERROR ノードのあるファイルが `files.error_lines > 0` になっている | 取りこぼしが静かに起きる |

**条件5・6 は実測で見つかった誤りに対応する。**
C# の誤り 22 件のうち 20 件が条件5、2 件が条件6 の違反だった。

### 4.3 ゴールデンデータとの突合

| # | 条件 |
|---|---|
| 1 | cJSON: `verdict='正'` の **50 行すべてが一致する** |
| 2 | FluentValidation: `verdict='正'` の **44 行すべてが一致する** |
| 3 | FluentValidation: `verdict='誤'` の 22 行が **`resolved` として出てこない**（§4.2 条件5・6 の適用で `ambiguous` / `external` になる） |

**条件3 が重要である。** 誤りを直したのだから、**同じ行が同じ誤り方で出てはならない。**
`correct_dst_file` が入っている行は、そこを指すか `unresolved` になるかのどちらかである。

## 5. 検証スクリプト

| スクリプト | 何を保証するか |
|---|---|
| `tools/schema-check/verify_schema.py` | **`SCHEMA.md` から DDL を抜き出して実行**し、文書に書いた性質（主キーの `NOT NULL`、衝突がエラーになること、結合の一意性、`extractor` での絞り込み、5レポートの中核クエリ、索引との一致）が実際に成り立つか |
| `tools/sample-golden.py` | ゴールデンデータの標本抽出 |

**`SCHEMA.md` を変更したら `verify_schema.py` を必ず走らせる。**
索引との突き合わせが入っているので、**列を足して索引を更新し忘れると落ちる**（実績あり）。

## 6. 回帰させないための記録

**数字を変えたら、出典のスクリプトも一緒に直す。**
過去に、同じ指標が測定スクリプトごとに **53 / 55 / 56** と食い違ったことがある。
原因は**3つのスクリプトが同じ判定を別々に書き直していた**ことだった。

**実装では判定規則を1箇所に置く**（`EXTRACTION.md` §5.2）。
テストもその1箇所を呼ぶ。**テスト用に判定を書き直さない。**
